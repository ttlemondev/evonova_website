### 实战项目：任务管理系统 (task-manager)

### 2.1 初始化任务管理系统

> 问题：怎么用 Claude Code 从零搭建一个新项目？
> 心智模型：描述需求，Claude 来选型

#### 动手：创建项目目录并启动 Claude

```bash
mkdir task-manager && cd task-manager
claude
```

> **跨平台提示**：上述命令在 macOS/Linux/PowerShell/Git Bash 中通用。如果你使用 Windows CMD，请改为 `mkdir task-manager & cd task-manager`（`&` 替代 `&&`）。

#### 动手：用一个提示词初始化项目

不指定技术栈，让 Claude 给方案：

```
> 我要做一个任务管理系统（类似简化版 Trello），需要前后端。
  核心功能：创建/查看/编辑/删除任务，任务有标题、描述、优先级（高/中/低）、
  状态（待办/进行中/已完成）、截止日期。
  帮我选择技术栈，给出 2-3 个方案，说明优缺点。
```

#### 观察

你会看到**类似**这样的方案对比（具体方案取决于 Claude Code 当时的判断，每次可能不完全一样）：

```
⏺ 我来分析几个可行的技术栈方案：

  方案 A：Next.js + Prisma + SQLite
    优点：全栈统一、部署简单...
    缺点：...

  方案 B：React + Express + PostgreSQL
    优点：前后端分离、灵活...
    缺点：...

  你倾向哪个方案？
```

选择你更熟悉的技术栈即可。如果不确定，选方案 A（Next.js 全栈）——课程后续示例都基于这个方案。

#### 动手：让 Claude 初始化项目

```
> 我选方案 X，帮我初始化项目：
  - 搭建前后端框架
  - 创建任务的数据库表（先不写业务逻辑）
  - 加几条示例任务数据
  - 确保 npm run dev 能跑起来，浏览器能看到页面
```

Claude Code 会开始执行，你会看到**类似**这样的权限确认：

```
⏺ 好的，我来初始化项目。

  Run: npm init -y                                          ← 权限确认，按 Enter 允许

  ● Allow   ○ Deny

⏺ 创建数据库表结构...

  Write: ...（数据库表结构文件）                       ← 创建文件

⏺ 添加示例数据...

  Run: npm run dev                                          ← 启动开发服务器

  ● Allow   ○ Deny
```

> Claude Code 会请求多次权限（安装依赖、创建文件、运行命令），逐一确认即可。

#### 验证

浏览器打开 `http://localhost:3000`（或 Claude Code 提示的端口），你应该能看到：
- 一个任务列表页面，显示 3-5 条示例任务
- 每条任务有标题、优先级标签（高/中/低，通常用红/黄/绿等颜色区分）
- 任务状态标签（待办/进行中/已完成）
- 截止日期显示

> **排错提示**：如果 `npm run dev` 报错，把错误信息复制给 Claude，让它帮你修复。常见原因包括端口占用、依赖未安装等。


> **初始化常见问题快查**：
>
> | 症状 | 可能原因 | 解决方法 |
> |------|---------|----------|
> | `npm install` 超时或报错 | 网络问题 / Node 版本不对 | 检查 Node 18+（`node -v`），换国内镜像：`npm config set registry https://registry.npmmirror.com` |
> | 端口 3000 被占用 | 其他服务占用 | `npx kill-port 3000`，或修改 `package.json` 的 dev 端口为 3001 |
> | 浏览器显示空白页 | 服务未完全启动 | 等待终端出现 `✓ Ready` 后再访问 |
> | WSL 下无法访问 | WSL 网络映射问题 | 用 `http://$(hostname -I | awk '{print $1}'):3000` 访问，或检查 WSL2 网络配置 |

#### 理论

这就是"Agentic 编程"的核心 — 你描述需求，Claude Code 选型 + 执行。

#### 动手：为项目创建 CLAUDE.md

任务管理器需要一份 CLAUDE.md，让 Claude 在后续所有操作中都遵循项目规范。在 Claude Code 中输入：

#### 动手：实现任务创建功能

**目标**：为任务管理器添加 POST /api/tasks 接口和前端创建表单，让用户能够新建任务。

在 Claude Code 中输入：

```
     - 包含 title 输入框、priority 下拉选择、提交按钮
```

- 刷新页面，刚才创建的任务仍然存在（已持久化）

> **排错提示**：如果提交表单后列表未刷新，把现象描述给 Claude，例如"POST 接口返回 201，但前端列表没有更新"。

### 2.2 实现任务的编辑和删除

> 问题：任务创建和查看已经有了，怎么让用户能改和删？
> 心智模型：增删改查，缺一不可

目前系统能创建任务、查看任务列表，但还不能修改或删除任务。US-1 要求完整的 CRUD 操作，本节补齐剩余的编辑和删除功能。

#### 动手：实现编辑任务

在 Claude Code 中输入：

```
> 帮我给 task-manager 添加编辑任务功能：
  - 后端：新增 PATCH /api/tasks/:id 接口，支持修改标题、描述、优先级（高/中/低）、状态（待办/进行中/已完成）、截止日期
  - 前端：在任务详情页或任务列表旁，添加"编辑"入口，点击后弹出或跳转到编辑表单，表单预填当前值，提交后更新显示
  - 所有字段都要做输入验证（标题不能为空，优先级和状态只接受预定义的值）
```

Claude 会大致按以下顺序执行：先更新数据模型（确认字段完整）→ 实现后端路由 → 实现前端编辑入口和表单 → 连接前后端。

#### 观察

Claude 执行期间，你会看到类似这样的操作序列：

```
⏺ Plan 分析：需要修改后端路由 + 新增前端编辑表单...

  Write: （后端路由文件）← 新增或修改 PATCH 接口
  Write: （前端编辑表单组件）← 预填当前任务数据的表单
  Write: （任务详情页或列表页组件）← 加上"编辑"按钮入口

⏺ 编辑功能完成，在浏览器中可以通过"编辑"按钮修改任务。
```

#### 验证：编辑任务

打开浏览器，在任务列表或详情页找到"编辑"入口，逐一确认：
- 点击"编辑"后，表单自动填入当前任务的标题、描述、优先级、状态、截止日期
- 修改优先级（比如从"低"改为"高"），保存后任务列表中的优先级标签立即更新
- 修改状态（比如从"待办"改为"进行中"），保存后状态标签更新
- 把标题清空后提交，系统拒绝并提示错误（验证生效）

> **排错提示**：如果编辑后页面没有更新，描述具体现象让 Claude 排查，例如"编辑保存后接口返回 200，但前端列表没有刷新"。

#### 动手：实现删除任务

```
> 帮我给 task-manager 添加删除任务功能：
  - 后端：新增 DELETE /api/tasks/:id 接口，删除指定任务及其所有关联评论
  - 前端：在任务列表和任务详情页添加"删除"按钮，点击后弹出确认弹窗（显示"确认删除任务《任务标题》吗？此操作不可撤销"），确认后执行删除并返回列表页
  - 如果任务不存在，接口返回 404
```

#### 观察

你会看到类似这样的执行过程：

```
⏺ 实现删除接口...

  Write: （后端路由文件）← 新增 DELETE 接口，级联删除评论
  Write: （前端确认弹窗组件）← 弹窗含任务标题和不可撤销提示
  Write: （任务列表页组件）← 删除成功后移除该条目

⏺ 删除功能完成。
```

#### 验证：删除任务

在浏览器中逐一确认：
- 点击某条任务的"删除"按钮，弹出确认弹窗，弹窗中显示该任务的标题
- 点击"取消"，弹窗关闭，任务仍然存在
- 点击"确认删除"，任务从列表中消失
- 刷新页面，被删除的任务不再出现（已持久化删除）

> 到 Ch7 时，PATCH `/api/tasks/:id` 接口会被看板视图复用，通过拖拽来更新任务状态，无需再写新接口。

#### 理论：为什么要在 Skill 实现功能之前先写完 CRUD？

完整的 CRUD 是后续所有功能的地基：
- 看板视图（Ch7）需要 **PATCH** 接口来更新任务状态
- MCP 数据查询（Ch8）需要完整的数据才有意义
- 安全审查（Ch3）审的是真实存在的接口，而不是空框架

先把基础写稳，后面每一章都是在这个地基上叠砖，而不是补漏洞。

### 2.3 体验现成的 Skill

> 问题：怎么让 Claude Code 按固定流程做事？
> 心智模型：SOP 给 AI 用

#### 动手：安装示例 Skill

在终端运行以下命令，让 Claude 帮你创建两个示例 Skill：

```
> 帮我在 ~/.claude/skills/ 目录下创建两个示例 Skill 文件：
  1. code-review/SKILL.md：按"安全→性能→可维护性"三个维度审查代码
  2. frontend-design/SKILL.md：检查 React 组件的可访问性和样式一致性
  每个文件只需要 frontmatter（name、description）和 3-5 步执行步骤即可
```

确认两个文件已创建：

```bash
ls ~/.claude/skills/
# 应看到 code-review/ 和 frontend-design/ 两个目录
```

#### 动手：用 /code-review 审查刚初始化的代码

```
/code-review
```

观察 Claude 的行为 — 它不是随便看看代码，而是按照 code-review Skill 定义的流程，**系统性地**审查。你会看到**类似**这样的结构化输出（具体内容因代码而异）：

```
⏺ 开始代码审查...

  📋 安全性检查
  - ⚠️ API 路由缺少输入验证
  - ✅ 无硬编码密钥

  📋 性能检查
  - ⚠️ 数据库查询未加索引
  - ✅ 无 N+1 查询问题

  📋 可维护性
  - ⚠️ 建议将数据库逻辑抽取到 repository 层
  - ✅ 文件结构清晰

  总结：发现 3 个建议改进项，0 个严重问题。
```

#### 动手：用 /frontend-design 改进任务列表页面

```
/frontend-design 改进 task-manager 的任务列表页面，
  要有优先级颜色标识、状态筛选、截止日期显示
```

#### 观察

Claude 执行时，你会看到类似这样的输出结构：

```text
⏺ 按照 frontend-design Skill 指引分析现有页面...

  Write: app/components/TaskList.tsx ← 添加优先级颜色标识
  Write: app/components/TaskFilter.tsx ← 新增状态筛选组件
  Write: app/page.tsx ← 集成筛选器和列表

⏺ 改进完成。
```

**关键观察点**：注意 Claude 输出时提到了“frontend-design Skill 指引”——这说明 Skill 的 `description` 和内容已经被 Claude 读取并作为约束。如果没有这个提示，说明 Skill 未被正确触发。

#### 验证：页面改进效果

在浏览器中逐项确认：
- 每条任务有颜色或标签区分优先级（高=红/橙，中=黄，低=绿/灰）
- 页面顶部有状态筛选器（全部 / 待办 / 进行中 / 已完成）
- 整体视觉上比初始化时的“最小可用版本”更整洁

> **排错提示**：如果页面没有变化，检查 Skill 文件是否在 `.claude/skills/frontend-design.md`，且 `allowed-tools` 包含了必要的工具（Write、Edit）。

如果没有出现筛选器，对 Claude 说：

```
> 在任务列表页面添加按状态筛选的选项（全部/待办/进行中/已完成），
> 调用 GET /api/tasks?status=xxx 接口，筛选结果替换当前列表显示
```

> **说明**：`GET /api/tasks?status=xxx` 接口在项目初始化时已随任务列表接口一起实现。如果筛选参数不生效，让 Claude 检查 API route 是否正确读取了 `searchParams.get('status')`。

#### 对比

如果你只说"帮我改进页面"，效果可能很随意。Skill 让 Claude 有一套**固定的执行清单**。

#### 理论：Skill 是什么？

```
Skill = 一个 Markdown 文件（SKILL.md），里面写着：
  - 什么时候用（description）
  - 怎么做（具体步骤和指引）
  - 用什么工具（allowed-tools）
  - 谁来触发（用户手动 vs Claude 自动判断）
```

Skill 和 CLAUDE.md 的区别：

| | CLAUDE.md | Skill |
|---|---|---|
| **管什么** | 规则（优先级分三级、日期格式统一） | 流程（添加功能的步骤） |
| **什么时候生效** | 始终生效 | 按需调用（手动或自动） |
| **粒度** | 项目级别的通用规范 | 一个具体任务的操作手册 |
| **类比** | 公司员工手册 | 某个岗位的 SOP |

### 2.4 自己造一个 Skill

> 问题：怎么把团队的最佳实践固化？
> 心智模型：写一次，人人用

#### 引出

现实中不同人写代码的方式不同，同样的需求可能产出完全不同的代码结构。我们来造一个 Skill，让所有人按同一套流程添加功能。

#### 动手：创建 add-feature Skill

```
> 帮我在 .claude/skills/add-feature/ 目录下创建一个 SKILL.md 文件，内容如下：

---
name: add-feature
description: 给 task-manager 添加新功能。当用户要求添加新的业务功能时使用。
---

# 添加功能

按照以下步骤为 task-manager 添加新功能：

1. 先用 Plan 模式分析需求，列出要改的文件
2. 定义相关的数据类型（TypeScript 类型或数据库表结构）
3. 实现后端逻辑（API 路由 + 业务逻辑）
4. 实现前端页面/组件
5. 所有输入必须做验证
6. 写完后在浏览器中手动验证功能
```

Claude Code 会确认文件创建，你会看到**类似**这样的输出：

```
⏺ 创建 Skill 文件...

  Write: .claude/skills/add-feature/SKILL.md                ← 创建 Skill 文件

  ✅ 已创建 .claude/skills/add-feature/SKILL.md
  现在你可以用 /add-feature 来触发这个 Skill。
```

> **US-2 回顾**：作为团队成员，我想给任务添加评论，和同事讨论进度和问题。
> - 验收标准：可以对任务添加文字评论；显示评论时间和作者；支持查看历史评论列表

#### 动手：用 Skill 添加"任务评论"功能（US-2）

```
/add-feature 添加"任务评论"功能：
  - 每个任务下面可以添加评论（评论内容 + 评论人姓名）
  - 任务详情页显示所有评论，按时间倒序
  - 可以删除自己的评论
```

#### 观察

Claude 会**大致**按 Skill 定义的步骤执行：先 Plan 分析 → 定义类型 → 后端 → 前端 → 验证。具体的执行顺序和细节每次可能略有不同，但整体流程是一致的。

#### 对比

不用 Skill 直接说"加评论功能"，Claude 可能跳过 Plan 分析，或把前后端逻辑混在一起。Skill 确保了**每次都按同一套流程执行**。

#### 验证

浏览器中打开一个任务的详情页，你应该能看到：
- 任务详情下方有一个评论输入区域（输入框 + 姓名框 + 提交按钮）
- 输入评论内容和姓名后点击提交，评论立即出现在列表中
- 评论按时间倒序排列（最新的在最上面）
- 每条评论显示内容、评论人姓名和时间
- 自己的评论旁边有删除按钮，点击可以删除

> **排错提示**：如果评论功能有 Bug（比如评论提交后没有显示、删除无反应），描述具体现象让 Claude 排查，例如"评论提交后页面没有更新，需要手动刷新才能看到"。

### 2.5 SKILL.md 的关键字段

> 问题：怎么控制 Skill 的触发和权限？
> 心智模型：精细控制，按需触发

#### 理论：frontmatter 完整配置

```yaml
---
name: add-feature
description: 给 task-manager 添加...
allowed-tools: [Edit, Write, Bash] # 限制工具范围
model: claude-sonnet-4-5          # 可选，以实际 CC 版本为准
---
```

| 字段 | 作用 | 任务管理项目示例 |
|------|------|-----------------|
| `name` | Skill 的唯一标识符，对应斜杠命令名 | `name: add-feature` |
| `model` | 指定使用的 Claude 模型（可选） | `model: claude-sonnet-4-5` |
| `description` | Claude 判断何时自动使用 | "当用户要求添加新的业务功能时使用" |
| `allowed-tools` | 限制工具范围 | 只读审查 Skill 只允许 Read、Grep |
| `arguments`（可选） | 定义命令参数，支持用户在调用时传入参数 | `/add-feature 添加评论功能` 中的参数描述 |

#### 动手：给 add-feature Skill 配置字段

打开你在 2.4 节创建的 add-feature Skill 文件，在文件最顶部的 frontmatter 中，补充以下字段（如果还没有的话）：

```yaml
---
name: add-feature
description: 标准化地为 task-manager 添加新功能，按 Plan → 类型 → 后端 → 前端 → 验证的顺序执行
allowed-tools: Read, Write, Edit, Bash, Grep, Glob
---
```

保存后，在 Claude Code 中输入：

```
/add-feature 添加"任务优先级筛选"功能
```

这条命令会触发你定义的 `add-feature` Skill，按 Plan → 类型 → 后端 → 前端 → 验证的标准流程自动执行。执行完成后，task-manager 应新增按优先级筛选任务的完整功能。你大致会看到：

- **后端**：任务查询接口新增 `priority` 查询参数（如 `?priority=high`），大致类似 `GET /api/tasks?priority=high` 这样的 API 支持
- **前端**：任务列表页出现优先级筛选器（高 / 中 / 低），选择"高"后列表只显示高优先级任务；切换为"全部"时恢复完整列表

**验证方式**：打开任务列表页，确认能看到优先级筛选 UI；选择"高"，观察列表是否只保留高优先级任务；再切换到"中"或"低"，验证筛选结果随之变化。如果以上行为符合预期，说明功能已成功添加。

观察：Claude 执行时，工具调用范围是否限制在 `allowed-tools` 列出的工具内？与没有配置 `allowed-tools` 时有什么不同？

> 如果当前 Skill 已经有 frontmatter，对照表格检查字段是否完整，补全缺少的字段即可。

### 2.6 Skill 的高级技巧

> 问题：Skill 怎么感知当前项目状态？
> 心智模型：动态感知，智能执行

#### $ARGUMENTS — 接收用户输入

`/add-feature 添加评论功能...` 中的 "添加评论功能..." 就是 `$ARGUMENTS`。

在 SKILL.md 中可以这样用：

```markdown
分析用户提供的需求："$ARGUMENTS"，然后按步骤执行...
```

#### 动态上下文注入 — `` !`command` ``

```
> @.claude/skills/add-feature/SKILL.md 帮我在步骤列表前面加上动态上下文：
  - 当前项目的文件结构概览（用 !`find . -name "*.ts" -o -name "*.tsx" | head -20`）
  - 当前已有的 API 路由（用 !`grep -r "router\.\|app\." --include="*.ts" -l`）
  这样 Skill 每次执行时都能看到项目当前状态
```

Claude 执行 Skill 时会先运行这些命令，把结果注入到上下文中。这样 Skill 每次执行时都能拿到**最新的项目状态**。

> **跨平台提示**：`find` 和 `grep -r` 是 Unix/macOS 命令。Windows 用户如果使用 Git Bash 或 WSL 则无需修改；如果使用 PowerShell，需要改用 `Get-ChildItem -Recurse -Filter "*.ts"` 等 PowerShell 等效命令。不过由于 Claude Code 本身运行在 bash 环境中，通常不需要担心这个问题。

#### 支持文件 — 给 Skill 附带模板

```
.claude/skills/add-feature/
├── SKILL.md              ← Skill 定义
├── component-template.tsx ← 前端组件模板
└── api-template.ts       ← API 路由模板
```

SKILL.md 中引用：`参考 component-template.tsx 的代码结构来创建新组件`。这样 Claude 生成的代码会更贴近你的团队风格。

### 2.7 Skill 的来源和共享

> 问题：好用的 Skill 怎么分享给团队？
> 心智模型：Git 提交，团队共享

#### Skill 存放位置

| 位置 | 谁能用 | 适用场景 |
|------|--------|---------|
| `~/.claude/skills/` | 只有你 | 个人常用的 Skill |
| `.claude/skills/` | 团队所有人（提交到 Git） | 团队共享的标准流程 |
| Plugin 中的 `skills/` | 安装了 Plugin 的人 | 社区/第三方提供 |

#### 动手：确认 Skill 被 Git 跟踪

```
> 帮我确认 .claude/skills/ 目录会被 Git 跟踪（不在 .gitignore 里），
  这样团队其他人 pull 代码后就能用 /add-feature 了
```

#### 动手：查找社区 Skill

CC 没有内置的 Skill 搜索命令。社区 Skill 主要通过 GitHub 分享，用以下关键词搜索：

```
https://github.com/search?q=claude-code+skills+typescript&type=repositories
```

打开链接，浏览排名靠前的仓库，重点看 `.claude/skills/` 目录下的 Markdown 文件，判断 Skill 的步骤定义是否清晰、工具权限是否合理。

常见社区 Skill 类型包括：`code-review`（代码审查）、`add-api-endpoint`（新增接口）、`write-test`（生成测试）。找到合适的后，直接把 SKILL.md 文件复制到你项目的 `.claude/skills/` 目录即可使用。

> 也可以直接问 Claude："有没有适合全栈 TypeScript 项目的 Skill 推荐？"——Claude 会给出方向性建议，但无法直接访问 GitHub，具体文件还是要自己找。

### 2.10 task-manager 核心 API 一览

Ch2 结束后，系统应该暴露以下 RESTful 接口。这张表也是 Ch7 看板视图和 Ch8 MCP 集成的依赖基础。

| 端点 | 方法 | 说明 | 涉及 US |
|------|------|------|---------|
| `/api/tasks` | GET | 获取任务列表，支持按状态、优先级筛选（`?status=xx&priority=xx`） | US-1 |
| `/api/tasks` | POST | 创建新任务 | US-1 |
| `/api/tasks/:id` | GET | 获取单个任务详情 | US-1 |
| `/api/tasks/:id` | PATCH | 更新任务字段（标题、优先级、状态、截止日期） | US-1 |
| `/api/tasks/:id` | DELETE | 删除任务及其所有关联评论 | US-1 |
| `/api/tasks/:id/comments` | GET | 获取任务的评论列表（按时间倒序） | US-2 |
| `/api/tasks/:id/comments` | POST | 给任务添加评论 | US-2 |
| `/api/comments/:id` | DELETE | 删除指定评论 | US-2 |

> 到 Ch7 时，PATCH `/api/tasks/:id` 会被看板视图复用来更新任务状态——当用户拖拽任务卡片到不同列时，前端直接调用这个接口，无需新增接口。

### 引出：代码多了，质量怎么保证？

Ch2 结束时，我们用 Skill 实现了 US-2 评论功能。评论相关的文件加进来后，项目结构已经有了一定规模。现在面临一个真实问题：

#### 理论：为什么要先 Explore 再 Plan？

如果跳过 Explore 直接 Plan，Claude 可能基于猜测的文件结构规划，产生"看起来合理但不适合你项目"的方案。先看再动，是一种专业习惯，也是 Agent 拆分的设计理念。

### 3.2 三个内置 Agent 的区别

> 问题：Explore、Plan 和通用 Agent 到底有什么不同？什么时候用哪个？
> 心智模型：用对工具，事半功倍

#### 动手：查看已有自定义 Agent

CC 没有 `/agents` 列表命令。自定义 Agent 存放在 `.claude/agents/` 目录，用 `ls` 查看已有 Agent，直接用 `/<agent-name>` 调用。

在终端中输入：

```
ls .claude/agents/
```

目前该目录为空（暂无自定义 Agent），3.3 节会创建第一个。

#### 理论：三类 Agent 的核心差异

| 特性 | Explore Agent | Plan Agent | 通用子代理（general-purpose） | 自定义 Agent |
|------|---------------|------------|------------------------------|-------------|
| 触发方式 | 自然语言触发，CC 自动派发 | 自然语言触发，CC 自动派发 | Claude 自动创建（无需手动） | `/<agent-name>` |
| 默认模型 | 轻量模型（Haiku 级别，CC 内部决定，仅供参考） | 中等模型（Sonnet 级别，CC 内部决定，仅供参考） | 与主对话相同 | 可在配置中指定 |
| 文件权限 | 只读 | 只读 | 继承主对话权限 | 可配置（只读 / 全权限） |
| 适用场景 | 快速了解现状 | 规划新功能或重构方案 | Claude 判断需要并行处理时自动使用 | 专项任务（安全审查、代码审计等） |
| 上下文隔离 | 独立上下文 | 独立上下文 | 独立上下文 | 独立上下文 |
| 可自定义 Prompt | 否 | 否 | 否 | 是（在 .md 文件正文中定义） |

**关键规律：**

- 内置 Agent（Explore / Plan / 通用子代理）是"开箱即用"的通用工具，快速但不可深度定制
- 自定义 Agent 是"量身定做"的专项工具，需要花时间配置，但专业度高

#### 平台注意事项

- **Windows**：斜杠命令在 Claude Code 的对话框中输入，和 Linux/macOS 完全一致
- **Linux/macOS**：无差异
- 自定义 Agent 的存放位置决定可用范围：个人全局配置在 `~/.claude/agents/`，项目级配置在项目根目录下的 `.claude/agents/`；用 `ls` 查看目录内容确认已有哪些 Agent

### 3.3 创建自定义 Agent：security-reviewer

> 问题：内置 Agent 不针对我的项目，怎么创建一个专门审查 task-manager 安全问题的 Agent？
> 心智模型：一次配置，随时唤醒

#### 引出

评论功能涉及用户输入（评论内容）、权限控制（谁能看谁的评论）、数据存储（评论写入数据库）。这些都是安全敏感点。内置的 Explore 和 Plan 不会主动帮你检查安全漏洞。我们需要一个专属的 `security-reviewer`，它知道要重点检查什么，每次都按同样的标准审查，不遗漏关键点。

#### 动手：创建 security-reviewer Agent 配置文件

在主对话中输入：

````
帮我在项目的 .claude/agents/ 目录下创建 security-reviewer.md 文件，内容如下：

---
name: security-reviewer
description: 安全审查员，专门审查 task-manager 代码的安全问题。当用户要求进行安全审查时使用。
model: claude-sonnet-4-5          # 可选，以实际 CC 版本为准
tools:
  - Read
  - Glob
  - Grep
permissionMode: readonly
maxTurns: 20
---

> **模型说明**：根据你的账号权限修改 `model` 字段。可选值：`claude-haiku-4-5-20251001`、`claude-sonnet-4-5`、`claude-opus-4-5`（均以实际安装的 CC 版本为准）。

# 安全审查员

你是 task-manager 项目的专属安全审查员。你的职责是仔细审查代码中的安全问题，给出具体的发现和可操作的修复建议。

**审查原则**

- 只读审查，不修改任何代码
- 发现问题按严重程度分级：严重 / 中等 / 建议
- 每个问题说明：位置（文件和大概行范围）、问题描述、修复建议

**重点检查项**

**1. 输入验证**
- 用户提交的评论内容是否有长度限制？
- 是否对特殊字符进行了过滤或转义？
- API 参数是否校验了类型和必填项？

**2. 权限控制**
- 查看评论是否需要登录？
- 删除/编辑评论是否只允许评论作者操作？

**3. 注入风险**
- 数据库查询是否使用了参数化查询或 ORM？
- 有没有直接把用户输入拼入 SQL 查询？

**4. 敏感数据**
- API 响应是否返回了不必要的字段（如密码 hash）？
- 错误消息是否泄露了内部实现细节？

**输出格式**

审查完成后，输出以下结构：

```
安全审查报告
============
审查范围：[说明审查了哪些文件/功能]

发现问题：
[严重] 问题标题
  位置：[文件描述]
  描述：[问题说明]
  建议：[修复方向]

总结：共发现 X 个问题（严重 X，中等 X，建议 X）
```
````

Claude Code 会确认文件创建，输出**类似**：

```
⏺ 创建 Agent 配置文件...
  Write: .claude/agents/security-reviewer.md
  ✅ 已创建 .claude/agents/security-reviewer.md

  Agent 配置说明：
  - 名称：security-reviewer
  - 模型：claude-sonnet-4-5
  - 权限：只读（permissionMode: readonly）
  - 可用工具：Read, Glob, Grep
  - 最大轮次：20
```

#### 动手：验证 Agent 文件已就位

CC 没有 `/agents` 列表命令。在终端中用 `ls` 确认文件已创建：

```
ls .claude/agents/
```

看到 `security-reviewer.md` 出现在目录中，说明 Agent 已就位，可以直接用 `/security-reviewer` 调用。

#### 观察

注意 Agent 配置文件的几个关键设计：

1. **`description` 字段**：这不只是备注，Claude Code 用这个描述判断"用户的请求是否应该触发这个 Agent"
2. **`tools` 限制**：只给了 Read、Glob、Grep 三个工具，限制工具就是限制风险边界。反过来，也可以用 `disallowedTools` 字段明确禁止某些工具（如 `disallowedTools: [Bash]` 禁止执行命令），两种方式按需选择
3. **`permissionMode: readonly`**：双重保险。即使 tools 配置有遗漏，readonly 模式也会阻止文件写入
4. **`maxTurns: 20`**：防止 Agent 陷入循环，20 轮足够完成一次完整的安全审查

#### 理论：Agent 配置文件的结构

一个 Agent 配置文件由两部分组成：

**Frontmatter（YAML 头部）**：机器读的配置

```yaml
---
name: security-reviewer           # Agent 名称，决定触发命令 /security-reviewer
description: ...                  # 触发时机描述，影响自动调用判断
model: claude-sonnet-4-5         # 使用的模型（以实际版本为准）
tools:                            # 允许使用的工具列表
  - Read
  - Glob
  - Grep
permissionMode: readonly          # 权限模式：readonly（只读）/ default（标准）
maxTurns: 20                      # 最大对话轮次
---
```

**正文（Markdown 内容）**：Agent 的系统提示词，写清楚职责、工作方式、输出格式。

**存放位置的区别：**

| 路径 | 作用范围 | 是否提交 Git |
|------|---------|-------------|
| `~/.claude/agents/` | 个人全局，所有项目可用 | 否（个人配置） |
| `.claude/agents/`（项目根目录） | 仅当前项目 | 建议提交，团队共享 |

### 3.4 用自定义 Agent 审查代码

> 问题：security-reviewer 创建好了，怎么让它真正工作？发现问题后怎么修复？
> 心智模型：发现问题，修复交付

#### 动手：用 security-reviewer 审查评论 API

在主对话中输入：

```
/security-reviewer 审查评论功能的 API 实现，重点检查输入验证和权限控制
```

Agent 启动后，你会看到它开始主动扫描文件，输出**大致**如下：

```
⏺ security-reviewer Agent 启动...
  [只读模式] 开始安全审查...

  扫描文件...
  ✓ 读取评论 API 路由文件
  ✓ 读取评论服务层文件
  ✓ 读取评论数据模型文件

  安全审查报告
  ============
  审查范围：评论功能相关的 API 实现

  [中等] 评论内容缺少长度限制
    位置：评论相关的 API 路由或服务文件
    描述：创建评论时，未对评论内容的最大长度进行校验。
    建议：在接收评论内容的地方，添加最大长度校验（如 1000 字符），超出时返回 400 错误。

  [中等] 删除评论未校验操作者身份
    位置：评论删除接口
    描述：删除评论时，只验证了用户是否登录，未验证该用户是否是评论的创建者。
    建议：删除前查询评论记录，对比 createdBy 字段和当前登录用户 ID，不匹配时返回 403。

  [建议] API 错误响应可以更规范
    位置：评论 API 的错误处理部分
    描述：部分错误响应直接返回了数据库错误信息，可能暴露内部实现细节。
    建议：统一错误响应格式，只返回用户友好的错误描述。

  总结：共发现 3 个问题（严重 0，中等 2，建议 1）

  ✅ 审查完成，未修改任何文件
```

#### 观察

注意几个细节：

1. **Agent 自主决定看哪些文件**：你只告诉它"审查评论 API"，它自己判断要读哪些文件
2. **输出格式符合配置**：报告结构和我们在 security-reviewer.md 正文中定义的格式一致
3. **只读确认**：报告最后明确"未修改任何文件"，这是 `permissionMode: readonly` 在起作用
4. **问题分级**：严重/中等/建议的分级帮助你决定优先处理什么

#### 动手：按审查报告修复问题

审查报告出来了，切回主对话（不是 security-reviewer Agent），处理发现的问题。以"删除评论未校验操作者身份"为例：

```
安全审查发现删除评论时没有校验操作者是否是评论作者。请修复这个问题，在删除评论的接口中，先查询评论记录，验证 createdBy 是否和当前登录用户匹配，不匹配时返回 403。
```

修复完成后，你可以再次运行 `/security-reviewer` 进行复核，确认问题已解决。

这个**"审查 → 修复 → 复核"**的循环是 Agent 辅助开发的基本工作模式。

#### 理论：Agent 与直接提问的本质区别

| 维度 | 直接提问 | 使用 Agent |
|------|---------|-----------|
| 上下文 | 共享主对话上下文，读大量文件会挤占空间 | 独立上下文，不影响主对话 |
| 标准一致性 | 每次可能检查不同的点 | 按配置文件中的检查清单，每次一致 |
| 工具权限 | 主对话的全部权限 | 按 Agent 配置限制，更安全 |
| 可复用性 | 下次还要重写提示词 | `/security-reviewer` 一行搞定 |
| 团队共享 | 只在你的对话历史里 | 配置文件提交 Git，团队共用 |

### 3.5 Agent 高级能力

> 问题：除了基本的审查，Agent 还能做什么更强大的事？
> 心智模型：Agent 越懂项目，越有价值

这一节介绍三个进阶能力，以理论为主。

#### 3.5.1 持久化记忆（通过文件实现）

**问题背景：** security-reviewer 每次启动都是空白状态，不记得上次发现了什么。

**实现方式：** Agent frontmatter 不支持 `memory` 配置字段。持久化记忆通过 CLAUDE.md 或项目文档实现——在 Agent 正文中明确指示 Agent 读取和写入固定路径的 Markdown 文件：

```yaml
---
name: security-reviewer
model: claude-sonnet-4-5          # 可选，以实际 CC 版本为准
tools:
  - Read
  - Glob
  - Grep
  - Write          # 需要写入记录文件
permissionMode: readonly
maxTurns: 20
---

每次审查结束后，将"严重"和"中等"问题追加写入 `.claude/memory/security-history.md`。
下次启动时先读取该文件，注明是否历史复发问题。
```

**记忆文件的作用域：**

| 作用域 | 路径示例 | 适用场景 |
|--------|---------|---------|
| **项目级** | `.claude/memory/security-history.md` | 记录特定项目的审查历史，提交 Git 后团队共享 |
| **用户级** | `~/.claude/memory/my-review-notes.md` | 记录个人跨项目的审查经验，私有 |

#### 动手：让 Agent 保留审查历史

修改 security-reviewer Agent 的指令内容，让它在每次审查后追加记录到记忆文件。在 Claude Code 中输入：

> 修改 .claude/agents/security-reviewer.md，在文件正文（frontmatter 下方的 Markdown 内容）末尾加入：
> "每次审查结束后，把发现的问题（格式：日期 + 文件 + 问题简述）追加写入 .claude/memory/security-history.md，如果文件不存在则创建。"

#### 观察

保存后，重新运行 `/security-reviewer` 审查任何一个 API 文件。审查完成后，检查 `.claude/memory/security-history.md` 是否自动生成，内容包含刚才发现的问题记录。

> 这个练习展示了 Agent 的持久化记忆能力：Agent 不只是在当前会话中输出结果，还能把结果写入文件，下次调用时可以读取历史记录，实现跨会话的状态积累。

#### 3.5.2 后台执行（当前版本特性说明，无需操作）

CC 2.1.x 中子代理由 CC 内部调度，无需在 frontmatter 中指定后台运行（`background` 字段不存在）。当你连续发送多条请求（如 3.6 节的多 Agent 并行），CC 会自动并行处理，主对话保持可响应。

适合大规模扫描的做法：拆分任务范围，分批触发 Agent，不阻塞主对话。

> 这是 CC 2.1.x 的内部调度机制说明，无需修改任何配置，了解即可。

#### 3.5.3 Agent 中使用 Skill（当前版本特性说明，无需操作）

Agent frontmatter 不支持 `skills` 字段，无法在配置中直接引用 Skill。

**实际做法：** 在 Agent 正文中说明调用 Skill 的格式。例如：

```
如需运行注入检查，在主对话中输入 /check-injection [文件路径]。
```

Agent 负责审查逻辑和汇总，Skill 负责可复用的具体检查脚本；两者通过 Agent 正文中的说明协作，而非 frontmatter 字段。

**可选验证：** 如果你在 3.5.1 中已经修改了 security-reviewer，重新运行 `/security-reviewer`，观察 Agent 输出中是否出现了"如需运行注入检查，在主对话中输入 /check-injection [文件路径]"的提示——这说明 Agent 正文的说明已经生效，可以引导后续的 Skill 调用。

#### 可选动手：让 security-reviewer 读取规范约束

在 `.claude/agents/security-reviewer.md` 的文件正文（frontmatter 下方的 Markdown 内容）开头加入：

> 审查前，先读取项目根目录的 CLAUDE.md 中的“API 规范”部分，把违反统一响应格式（`{ success, data, error }`）的代码额外标注为 [规范违反]。

保存后重新运行 `/security-reviewer`，观察输出中是否新增了“[规范违反]”标记——这说明 Agent 已成功读取了 CLAUDE.md（一个结构化文本文件，相当于项目级 Skill 的静态约束版本）。

#### 3.5.4 Agent 与 Hook 结合

> **注意**：以下配置涉及 Hook 概念，将在 Ch4 中详细讲解。这里提前展示是为了说明 Agent 和 Hook 的组合用法——你可以先跳过细节，Ch4 学完后再回来理解这段配置。

Agent 和 Hook 可以协同工作：在 `settings.json` 中配置 Hook，让安全审查结果自动触发后续操作。例如，在 Stop Hook 中检测 security-reviewer 的输出，决定是否阻止本次对话结束：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/hooks/check-dangerous.sh"
          }
        ]
      }
    ]
  }
}
```

Hook 配置在 `settings.json` 中，Agent 负责审查、Hook 负责自动化响应，两者通过文件或退出码协作。

### 3.6 多 Agent 协作

> 问题：一个 Agent 专注一个角度，能不能同时从多个角度审查同一个功能？
> 心智模型：并行分工，结论互补

#### 引出

security-reviewer 只关注安全。但评论功能还可能有代码质量问题、性能问题。如果三件事要顺序做，效率低。更好的方式是：三个 Agent 同时启动，各自独立工作，三份报告一起出来。

#### 动手：并行启动三个 Agent

在主对话中，连续发送三条消息（快速依次发送，不需要等上一个完成）：

```
分析评论功能涉及的文件结构，列出所有相关文件和它们的依赖关系。请使用只读模式，不要修改任何文件。
```

```
/security-reviewer 审查评论 API 的安全问题，重点关注输入验证和权限控制
```

```
帮我规划评论统计功能的实现方案，评估对现有评论功能代码的影响。只输出规划方案，不要写代码。
```

> **注意**：Explore Agent 和 Plan Agent 均由 CC 内部自动派发，使用自然语言触发。只有自定义 Agent（如 `/security-reviewer`）才通过 `/<agent-name>` 调用。

#### 观察

三个命令发出后：

1. **独立运行**：三个 Agent 各自在独立的上下文中工作，互不干扰
2. **结果各有侧重**：Explore 给文件地图，security-reviewer 给安全报告，Plan 给实现规划
3. **主对话保持空闲**：三个 Agent 运行期间，主对话仍然可以响应你的输入

三份报告都出来后，你在主对话中综合三个视角做决策。

#### 理论：多 Agent 协作的适用场景

**适合并行的情况：**

- 多个 Agent 审查同一份代码的不同维度（安全 / 性能 / 质量）
- 多个功能模块的独立审查（互不依赖时可以同时审查）
- 探索 + 规划同步进行

**不适合并行的情况：**

- Agent B 的输入依赖 Agent A 的输出（必须顺序执行）
- 两个 Agent 都要写同一个文件（会产生冲突）

**主对话的角色：** 在多 Agent 协作中，主对话扮演"指挥官"角色——下达任务、收集结果、综合判断、决定下一步。Agent 是"专项执行者"，执行明确的任务，向指挥官汇报。

## Ch4 Hook — 写代码时自动检查


> 本章实现 **US-4：危险命令拦截 + 代码自动格式化**
>
> 验收标准：
> - 配置 PreToolUse Hook，执行含 `rm -rf` 的命令时自动拦截并打印警告，命令不执行
> - 配置 PostToolUse Hook，编辑 `.ts` 文件后自动运行 `prettier`，无需手动触发
> - 在 `.claude/settings.json` 中查看两条 Hook 配置，确认结构正确

> 预计时长：40 分钟

---

### 引出

在 Ch2 中，你用 Claude Code 完成了评论功能。回想一下整个过程：Claude 写完代码后，你要手动运行格式化工具，手动跑测试看有没有过，偶尔还担心 Claude 会不会执行了什么危险命令。

能不能让这些事情自动发生？

**能。这就是 Hook 的作用。**

Hook 是 Claude Code 生命周期中的自动触发器。本章结束时，你的 task-manager 项目会拥有：写 TypeScript 文件后自动格式化、执行危险命令前自动拦截、任务完成后自动跑测试——全部无需手动操作。

### 4.1 第一个 Hook：写 .ts 文件后自动格式化

> 问题：Claude 修改 TypeScript 文件后，格式化要手动跑，能不能自动化？
> 心智模型：改完即整洁

#### 动手：让 Claude 创建 Prettier Hook 配置

打开 task-manager 项目，对 Claude 说：

```
帮我在 .claude/settings.json 的 hooks 字段里添加一个 PostToolUse Hook：
当 Claude 执行 Write 或 Edit 工具（写文件/编辑文件）后，
自动运行 prettier --write 格式化被修改的文件。
被修改的文件路径通过 $CLAUDE_FILE_PATHS 环境变量获取。
```

Claude 会修改（或创建）`.claude/settings.json`，内容**大致**如下：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "prettier --write \"$CLAUDE_FILE_PATHS\""
          }
        ]
      }
    ]
  }
}
```

#### 动手：验证 Hook 生效

现在触发这个 Hook，对 Claude 说：

```
给任务评论功能的输入验证添加一条规则：评论内容不能超过 500 字符，
超出时返回 400 错误并提示“评论内容不能超过 500 字符”。
```

Claude 修改完评论相关的 TypeScript 文件后，你会看到**类似**这样的输出：

```
⏺ 修改评论数据类型...
  Edit: [评论相关的 TypeScript 文件]  ← Claude 编辑文件
  ✅ 已修改

⏺ Running hook: PostToolUse
  $ prettier --write "[文件路径]"
  [文件路径] 42ms   ← Prettier 自动运行
```

打开被修改的文件，缩进、引号、分号都已经被 Prettier 统一整理好，不需要你手动做任何事。

#### 观察

注意几个关键现象：

- Hook 在 Claude 完成工具调用**之后**立即触发，不需要用户确认
- `$CLAUDE_FILE_PATHS` 包含了本次被修改的文件路径，Prettier 只处理这些文件，不会扫描整个项目
- 如果 Prettier 未安装，Hook 会报错——这时 Claude 通常会提示你先安装依赖

#### 理论：PostToolUse 的执行时机

PostToolUse Hook 在某个工具**成功执行完毕后**触发。上面配置的含义：

| 字段 | 值 | 含义 |
|------|----|------|
| `matcher` | `"Write\|Edit"` | 匹配 Write 工具或 Edit 工具 |
| `type` | `"command"` | 执行 Shell 命令 |
| `command` | `"prettier --write ..."` | 要执行的命令 |

`matcher` 是正则表达式，`Write|Edit` 表示"Write 或 Edit 任意一个匹配就触发"。`$CLAUDE_FILE_PATHS` 是 Claude Code 注入的环境变量，值为本次操作涉及的文件路径（多文件时以空格分隔）。

### 4.2 理论：Hook 是什么？

> 问题：Hook 是一个什么样的概念，和 Git Hook 有什么关系？
> 心智模型：生命周期里的检查站

#### 动手：查看当前 Hook 配置

在 Claude Code 里输入：

```
/hooks
```

你会看到一个交互式管理界面，列出当前项目配置的所有 Hook。刚才创建的 Prettier Hook 出现在列表里。

#### Git Hook 类比

如果你用过 Git Hook，Hook 的概念会很好理解：

| Git Hook | Claude Code Hook | 触发时机 |
|----------|-----------------|---------|
| `pre-commit` | `PreToolUse` | 工具执行**前**（可以拦截） |
| `post-commit` | `PostToolUse` | 工具执行**后**（处理结果） |
| `post-push` 类比 | `Stop` | Claude 完成整个任务后 |
| — | `Notification` | Claude 主动向用户发送通知时（如长时间任务的进度更新） |
| — | `SubagentStart` | 子代理启动时（实验性，待验证） |
| — | `SubagentStop` | 子代理完成时（实验性，待验证） |

Git 在 commit 前运行 pre-commit Hook 检查代码，Claude Code 在执行工具前运行 PreToolUse Hook 做验证——逻辑完全一致。

#### 六种事件类型

**PreToolUse**：工具执行前触发。可以检查参数，如果返回非 0 退出码，工具会被拦截，命令不会执行。适合做安全检查、参数验证。*task-manager 示例：执行 `rm -rf` 删除数据库文件前，自动拦截并提示手动确认。*

**PostToolUse**：工具执行后触发。无法阻止已经发生的操作，但可以做后处理——格式化、lint、记录日志等。*task-manager 示例：修改 `.ts` 文件后，自动运行 Prettier 保持代码风格一致。*

**Stop**：Claude 完成整个任务（对话结束或任务完成）后触发。适合做最终验证：跑测试、生成报告等。注意：Stop Hook 本身也会触发新的 Stop 事件，必须防止无限循环（4.4 节详细说明）。*task-manager 示例：会话结束前，自动检查是否有 `console.log` 遗留在已修改的文件中。*

**Notification**：Claude 主动向用户发送通知时（如长时间任务的进度更新）触发。可以用来发送通知（比如发 Slack 消息："Claude 在等你确认一个操作"）。*task-manager 示例：Claude 等待用户确认删除操作时，记录操作日志到 `.claude/logs/` 目录。*

**SubagentStart / SubagentStop**：子代理启动时和完成时触发。可以用来记录 Agent 的执行日志、统计 Agent 运行时长，或在子代理完成后自动汇总报告。*task-manager 示例：代码审查子代理完成后，自动将审查摘要写入 `.claude/logs/review.log`。*

> **注意**：`SubagentStart` 和 `SubagentStop` 在 CC 2.1.x 官方文档中暂无明确记录，能否实际触发需以实际版本为准。

#### 理论：Hook 存储在哪里？

Hook 配置存储在 `.claude/settings.json` 的 `hooks` 字段里。这个文件是项目级配置，提交到 Git 后，团队所有人共享同一套 Hook。

```
task-manager/
├── .claude/
│   └── settings.json   ← Hook 配置在这里
├── src/
└── ...
```

如果需要个人级 Hook（不提交到 Git），也可以配置在 `~/.claude/settings.json`（用户全局配置），但团队协作场景更推荐项目级配置。

### 4.3 危险命令拦截：PreToolUse Hook

> 问题：Claude 偶尔会执行危险的 Bash 命令，能不能在执行前自动拦截？
> 心智模型：执行前先过筛

#### 动手：让 Claude 创建危险命令拦截 Hook

对 Claude 说：

```
帮我创建一个 PreToolUse Hook，在 Claude 执行 Bash 命令前做安全检查：
如果命令包含 rm -rf、DROP TABLE、TRUNCATE、> /dev/sda 这类危险操作，
就拒绝执行（返回非 0 退出码并输出警告信息）。
把检查逻辑写在 .claude/hooks/check-dangerous.sh 脚本里，
Hook 配置里调用这个脚本。

注意：
- 普通的 rm 命令（比如 rm 某个具体文件）不应该被拦截
- 只拦截明显危险的模式
- 拦截时输出清晰的警告，说明被拦截的原因
```

Claude 会创建两个东西：

**1. 拦截脚本** `.claude/hooks/check-dangerous.sh`，内容**大致**如下：

```bash
#!/bin/bash

# PreToolUse Hook 通过 stdin 接收 JSON，格式：{"tool_name":"Bash","tool_input":{"command":"..."}}
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | python3 -c "import json,sys; d=json.load(sys.stdin); print(d.get('tool_input',{}).get('command',''))" 2>/dev/null || echo "")

# 定义危险模式（正则）
DANGEROUS_PATTERNS=(
  "rm[[:space:]]+-[^[:space:]]*r[^[:space:]]*[[:space:]]+-[^[:space:]]*f"
  "rm[[:space:]]+-rf"
  "DROP[[:space:]]+TABLE"
  "TRUNCATE[[:space:]]+TABLE"
  ">[[:space:]]*/dev/sd"
)

for pattern in "${DANGEROUS_PATTERNS[@]}"; do
  if echo "$COMMAND" | grep -iE "$pattern" > /dev/null 2>&1; then
    echo "⚠️  [Hook 拦截] 检测到危险命令模式: $pattern"
    echo "被拦截的命令: $COMMAND"
    echo "如需执行，请手动在终端运行。"
    exit 2
  fi
done

exit 0
```

**2. Hook 配置**，在 `.claude/settings.json` 里新增 PreToolUse：

```json
{
  "hooks": {
    "PostToolUse": [ "..." ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/hooks/check-dangerous.sh"
          }
        ]
      }
    ]
  }
}
```

> **Windows 用户注意**：`.sh` 脚本需要在 Git Bash 或 WSL 环境中运行。如果你使用 Git Bash，确认 Claude Code 终端使用的是 Git Bash。如果使用 WSL，路径需要调整为 WSL 格式。

### 4.4 自动测试：Stop Hook

> 问题：每次 Claude 改完代码后，测试要手动跑，能不能自动化？
> 心智模型：收尾即验收

#### 引出：Stop Hook 的特殊性

任务执行完毕、Claude 准备结束会话时，怎么确保最后一次检查不被遗漏？答案是：在会话结束（Stop 事件）时触发一个自动验证脚本，这就是 Stop Hook 的价值所在。

Stop Hook 在 Claude **完成整个任务后**触发，是做最终验证的理想位置。但它有一个关键陷阱：

**Stop Hook 自身也是一个工具调用**，如果 Stop Hook 触发了新的操作，那个操作完成后又会触发 Stop Hook，形成**无限循环**。

Claude Code 为此提供了 `stop_hook_active` 环境变量：当 Stop Hook 正在运行时，这个变量被设为 `"true"`。你必须在脚本开头检查它。

#### 动手：让 Claude 创建 Stop Hook

对 Claude 说：

```
帮我创建一个 Stop Hook，在 Claude 完成任务后自动运行项目的测试套件。
要求：
1. 必须检查 stop_hook_active 环境变量，如果是 true 就直接退出，防止无限循环
2. 用项目配置的测试命令运行测试（类似 npx vitest run --reporter=verbose）
3. 测试失败时输出明显的提示
```

Claude 修改 `.claude/settings.json`，新增 Stop Hook，配置**大致**如下：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "if [ \"$stop_hook_active\" = \"true\" ]; then exit 0; fi && npx vitest run --reporter=verbose"
          }
        ]
      }
    ]
  }
}
```

或者 Claude 可能会创建一个独立脚本 `.claude/hooks/run-tests.sh`：

```bash
#!/bin/bash

# 防止无限循环：如果 Stop Hook 已在运行，直接退出
if [ "$stop_hook_active" = "true" ]; then
  exit 0
fi

echo "🧪 [Stop Hook] 任务完成，自动运行测试..."
npx vitest run --reporter=verbose

EXIT_CODE=$?
if [ $EXIT_CODE -ne 0 ]; then
  echo ""
  echo "❌ [Stop Hook] 测试失败！请检查上方的错误信息。"
fi

exit $EXIT_CODE
```

#### 动手：验证 Stop Hook 生效

对 Claude 说：

```
给评论功能的输入验证添加一条规则：评论内容不能为空字符串（trim 后长度必须大于 0）。
```

Claude 修改评论相关的验证逻辑。任务完成后，你会看到**类似**这样的输出：

```
⏺ 修改完成。

⏺ Running hook: Stop
  🧪 [Stop Hook] 任务完成，自动运行测试...

  ✓ 评论内容验证 > 拒绝空字符串 (12ms)
  ✓ 评论内容验证 > 允许正常评论 (3ms)
  ✓ 任务创建 > 基础流程 (8ms)
  ...
  Test Files  3 passed (3)
  Tests       12 passed (12)
  Duration    1.23s
```

如果测试失败，Claude 会看到失败信息，并通常会主动提出修复。

#### 观察

注意 Stop Hook 和 PostToolUse Hook 的区别：

- **PostToolUse**：每次工具调用后都触发（Claude 修改一个文件就触发一次）
- **Stop**：整个任务完成后只触发一次

如果 Claude 在一次任务里修改了 5 个文件，PostToolUse Hook 会触发 5 次，Stop Hook 只触发 1 次。对于"跑测试"这种操作，放在 Stop 更合理——不需要每改一个文件就跑一遍完整测试套件。

#### 理论：stop_hook_active 的工作原理

当 Stop Hook 运行时，Claude Code 会将 `stop_hook_active` 设为 `"true"` 并注入到 Hook 进程的环境变量里。你的脚本读到这个值，就知道"我是被 Stop Hook 调用的"，应该直接退出，不能再触发新的逻辑。

这是一个**约定大于配置**的防护机制——Claude Code 提供了变量，但必须由你的脚本主动检查。不检查，无限循环的锅由你来背。

### 4.5 三种 Hook 类型

> 问题：除了执行 Shell 命令，Hook 还能做什么？
> 心智模型：命令、AI、代理三层

前面用的都是 `command` 类型的 Hook。Claude Code 实际提供了三种 Hook 类型，能力依次递增，成本也依次递增。

> **说明**：`command` 类型已在 CC 2.1.x 官方文档中明确记录（已确认）。`prompt` 和 `agent` 类型在 CC 2.1.x 官方文档中暂未明确记录，属实验性功能，以实际版本为准。

#### command Hook（最常用）

**适用**：执行 Shell 脚本、CLI 工具、简单检查。

**特点**：速度快，无额外费用，适合大多数自动化场景。

**示例**：

```json
{
  "type": "command",
  "command": "eslint \"$CLAUDE_FILE_PATHS\" --fix"
}
```

典型用途：Prettier 格式化、ESLint 检查、文件权限检查、日志记录。

#### prompt Hook（更智能）

**适用**：需要 AI 理解上下文做判断的场景，比如"这次修改有没有引入硬编码的密码？"

**特点**：调用 LLM 分析内容，能理解语义，但每次触发都消耗 token，成本比 command 高。

**配置示例**：

```json
{
  "type": "prompt",
  "prompt": "检查以下被修改的代码，判断是否包含硬编码的密钥、密码或 token。如果有，输出 BLOCK 并说明原因；如果没有，输出 ALLOW。\n\n被修改的文件：$CLAUDE_FILE_PATHS"
}
```

prompt Hook 的返回内容会传回 Claude Code，Claude Code 根据内容决定是否继续。

#### agent Hook（最强大）

**适用**：需要复杂验证逻辑的场景，比如调用专门的 security-reviewer Agent（就是你在 Ch3 创建的那个）对每次修改做完整安全审查。

**特点**：启动一个完整的子代理，有完整的工具调用能力，能读文件、搜索代码、做多步分析。最强大，也最昂贵。

**配置示例**：

```json
{
  "type": "agent",
  "agent": "security-reviewer"
}
```

这里 `security-reviewer` 对应 `.claude/agents/security-reviewer.md` 文件（Ch3 创建的那个 Agent）。每次触发这个 Hook，Claude Code 会启动一个子代理，用 security-reviewer 的 System Prompt 和工具权限，对当前上下文做分析。

> ⚠️ **实验性功能提示**：`prompt` 和 `agent` 类型在 CC 2.1.x 中属于实验性功能，以实际安装版本为准。如果配置后未触发预期行为（Hook 无响应或报错），请改用 `command` 类型替代：
> - `prompt` Hook 替代：将检查逻辑写成 Shell 脚本（如 `grep -r "password\s*=" $CLAUDE_FILE_PATHS`），用 `command` 类型执行
> - `agent` Hook 替代：手动调用 `/security-reviewer`，而非依赖 Hook 自动触发
>
> 串联练习中如果 `agent` Hook 未生效，直接手动运行 `/security-reviewer` 作为替代，练习目标不变。

#### 动手：理解三种类型的适用场景

对照 task-manager 项目，思考每种类型的合适位置：

| 场景 | 推荐类型 | 理由 |
|------|---------|------|
| 写 .ts 文件后格式化 | command | 纯工具调用，速度要求高 |
| 拦截危险 Bash 命令 | command | 规则明确，正则匹配即可 |
| 检查是否引入硬编码密钥 | prompt | 需要语义理解，规则难以穷举 |
| 对重大功能修改做安全审查 | agent | 需要 security-reviewer 的完整分析能力 |

### 4.6 Matcher 模式

> 问题：如何精确控制哪个工具触发哪个 Hook？
> 心智模型：正则筛工具不误伤

#### Matcher 是正则表达式

Matcher 字段的值是正则表达式，匹配的对象是**工具名**。Claude Code 内置的工具名包括：

| 工具名 | 触发时机 |
|--------|---------|
| `Write` | 创建新文件 |
| `Edit` | 编辑现有文件 |
| `Bash` | 执行 Shell 命令 |
| `Read` | 读取文件内容 |
| `Glob` | 文件模式搜索 |
| `Grep` | 内容搜索 |
| `mcp__[服务名]__[工具名]` | 调用 MCP 工具 |

常用 Matcher 示例：

```
"Write|Edit"          → 写文件或编辑文件（最常用）
"Bash"                → 执行 Shell 命令
"Write|Edit|Bash"     → 文件操作或命令执行
"mcp__.*"             → 任何 MCP 工具调用
"mcp__database__.*"   → 特定 MCP 服务的所有工具
```

#### 在脚本里进一步过滤文件类型

Matcher 只能匹配工具名，无法直接过滤"只在修改 .ts 文件时触发"。要做文件类型过滤，需要在脚本里判断 `$CLAUDE_FILE_PATHS` 的扩展名：

```bash
#!/bin/bash

# 只处理 .ts 和 .tsx 文件
for file in $CLAUDE_FILE_PATHS; do
  if [[ "$file" == *.ts ]] || [[ "$file" == *.tsx ]]; then
    prettier --write "$file"
  fi
done
```

#### 动手：优化 Prettier Hook

当前的 Prettier Hook 对所有 Write/Edit 都触发，包括 `.json`、`.md`、`.sh` 文件。对 Claude 说：

```
优化 Prettier Hook，让它只处理 .ts 和 .tsx 文件。
把 prettier 命令从直接写在 command 里改为调用一个脚本 .claude/hooks/prettier-ts.sh，
脚本里检查文件扩展名，只格式化 TypeScript 文件。
```

Claude 会创建脚本并更新配置，这样 Prettier Hook 就不会干扰其他类型的文件了。

### 5.2 CLAUDE.md vs settings.json — 分工明确

| 维度 | CLAUDE.md | settings.json |

- `CLAUDE.md` 回答"AI 应该写出什么样的代码"
- `settings.json` 回答"工具应该怎么运行"

### 5.3 三层配置体系与优先级

> 问题：如果多个地方都有配置，以哪个为准？
> 心智模型：三层覆盖，就近优先

#### 动手：查看三个配置文件的位置

在 task-manager 项目里，让 Claude 检查三个配置文件：

```
> 帮我查看以下三个位置是否有配置文件，有的话展示内容：
  1. ~/.claude/settings.json（用户全局配置）
  2. .claude/settings.json（项目共享配置，当前目录）
  3. .claude/settings.local.json（项目本地配置，当前目录）
```

**注意平台差异**：

- **Windows**：`~` 对应 `C:\Users\你的用户名`，即 `C:\Users\你的用户名\.claude\settings.json`
- **macOS/Linux**：`~` 对应 `/Users/你的用户名` 或 `/home/你的用户名`

#### 观察：可能的情况

- 全局配置（`~/.claude/settings.json`）：大概率已存在，记录了你在其他项目里设置过的全局偏好
- 项目配置（`.claude/settings.json`）：Ch4 已经创建，里面有 Hook 配置
- 本地配置（`.claude/settings.local.json`）：可能还不存在（我们马上创建它）

#### 理论：三层结构详解

```
优先级（从高到低）：

┌─────────────────────────────────────────────────────┐
│  .claude/settings.local.json   ← 最高优先级（本地）  │
│  （项目本地，不提交 Git）                            │
├─────────────────────────────────────────────────────┤
│  .claude/settings.json         ← 项目优先级（共享）  │
│  （项目共享，提交 Git）                              │
├─────────────────────────────────────────────────────┤
│  ~/.claude/settings.json       ← 最低优先级（全局）  │
│  （用户全局，所有项目共用）                          │
└─────────────────────────────────────────────────────┘
```

**托管策略（企业管理员，了解即可）**：

除了上面三层，企业管理员还可以通过 **Managed Policy** 强制下发配置（如禁止使用某些工具、强制指定模型等）。托管策略的优先级最高，会覆盖所有本地配置，普通开发者无法修改。这在需要统一管控的企业环境中很有用，但通常由 IT 团队配置，开发者只需知道这个机制存在即可。

**合并机制（重要）**：

不是"高优先级完全替换低优先级"，而是**合并（merge）**：

- 低优先级的配置作为基础
- 高优先级的配置在合并时**覆盖同一个 key**
- 低优先级里有但高优先级里没有的 key，**依然生效**

举例：

```json
// ~/.claude/settings.json（全局，低优先级）
{
  "model": "claude-sonnet-4-5",
  "env": {
    "LOG_LEVEL": "info"
  }
}

// .claude/settings.json（项目，中优先级）
{
  "hooks": {
    "PostToolUse": ["..."]
  }
}

// 合并结果（最终生效）：
// model 来自全局，hooks 来自项目，env 来自全局
{
  "model": "claude-sonnet-4-5",
  "hooks": { "PostToolUse": ["..."] },
  "env": { "LOG_LEVEL": "info" }
}
```

#### 动手：验证优先级

通过一个实验亲眼验证优先级。让 Claude 帮你创建 local 配置文件：

```
> 在 .claude/settings.local.json 里写入以下内容：
  {
    "model": "claude-haiku-4-5-20251001"
  }
  这个文件如果不存在就创建它。
```

然后让 Claude 执行一个轻量任务并说明它用的是哪个模型：

```
> 列出 src/ 目录下的文件。
  执行前先告诉我：你当前使用的是哪个模型？
```

#### 观察：local 配置生效

Claude 应该汇报它使用的是 haiku 模型（即 `settings.local.json` 里指定的），而不是项目配置里的 sonnet。这就是就近优先原则的体现。

> **提示**：验证完成后，如果你不想一直用 haiku，可以让 Claude 删除 `settings.local.json` 里的 model 字段，或者删除整个文件。

### 5.4 各层级的典型用途

> 问题：什么配置该放在哪一层？放错了会有什么问题？
> 心智模型：私有留本地，共享入仓

#### 动手：审查 task-manager 的配置分层

让 Claude 帮你梳理当前配置的分层是否合理：

```

  告诉我哪些配置放对了层级，哪些可能需要调整。
```

#### 观察：Claude 的分析

Claude 大致会指出类似问题：

- 如果 `model` 写在了 `.claude/settings.json`（项目共享），意味着整个团队都被锁定在同一个模型，可能不够灵活
- 个人调试用的环境变量不应该出现在提交 Git 的配置里

#### 理论：三层用途速查表

| 层级 | 文件路径 | 提交 Git | 适合放什么 |
|------|----------|----------|-----------|
| **用户全局** | `~/.claude/settings.json` | 不提交（个人机器） | 个人编辑器偏好、个人全局 Hook（如全局 Prettier）、个人 MCP 服务（本地数据库连接）、个人危险命令拦截 |
| **项目共享** | `.claude/settings.json` | **提交** | 团队规范 Hook、项目级 `allowedTools`、团队共享 MCP 配置、项目标准模型（可选） |
| **项目本地** | `.claude/settings.local.json` | **不提交** | 个人覆盖团队设置、本地调试配置、不想进 Git 的敏感信息、个人省 token 的模型选择 |

#### task-manager 团队场景示例

**场景**：团队 5 人，用同一个 task-manager 仓库。

```

- allowedTools 包含 npm run test 和 npm run build
- 团队共享的 MCP 数据库连接（测试环境）

小明在 .claude/settings.local.json（不提交）里个人配置：
- model 改成 haiku（省自己账户的 token）
- 本地数据库的连接字符串（不想提交到 Git）
- 一个只有他用的调试 Hook

小红在 ~/.claude/settings.json（全局）里个人配置：
- 全局 Prettier（所有项目都自动格式化）
- 她常用的 MCP 工具
```

根据上面的理论，让 Claude 帮你规范配置分层：

```

  1. 把 .claude/settings.json 里属于个人偏好的内容移到 settings.local.json
```

### 5.5 常用配置项速查

> 问题：settings.json 到底能写哪些字段，每个字段怎么用？
> 心智模型：四类字段，各司其职

#### 动手：查询某个配置项的用法

遇到不熟悉的配置项时，直接问 Claude：

```
> allowedTools 这个配置项怎么用？
  比如我只想允许运行 npm run test，不允许运行其他 npm 命令，
  具体怎么写？
```

#### 观察：Claude 的解释

Claude 会给出类似这样的精确格式说明：

```json
{
  "permissions": {
    "allowedTools": [
      "Bash(npm run test)"
    ]
  }
}
```

并解释 `Bash(精确命令)` 的格式：括号里是精确的命令字符串，只有这条命令会被自动允许，其他 Bash 命令仍然需要确认。

#### 理论：四大配置类别

**1. permissions（权限控制）**

```json
{
  "permissions": {
    "allowedTools": [
      "Bash(npm run test)",
      "Bash(npm run build)",
      "Bash(npm run lint)",
      "Bash(git status)",
      "Bash(git diff)"
    ],
    "disallowedTools": []
  }
}
```

- `allowedTools`：列表里的工具/命令**不需要用户确认**直接执行
- `disallowedTools`：列表里的工具/命令**完全禁止**，Claude 不会尝试使用
- `Bash(具体命令)` 格式：精确匹配，只允许括号里这条命令，安全性更高
- 不带括号的 `"Bash"` 则允许所有 Bash 命令（慎用）

**2. hooks（自动化钩子）**

详见 Ch4，结构回顾：

```json
{
  "hooks": {
    "PreToolUse": ["..."],
    "PostToolUse": ["..."],
    "Stop": ["..."]
  }
}
```

**3. model（模型设置）**

```json
{
  "model": "claude-sonnet-4-5"
}
```

- 指定默认使用的模型
- 交互式切换模型可用 `/model` 命令（只对当前会话生效）
- `settings.json` 里的 `model` 是持久化配置（每次启动都生效）
- 常用模型名参考：`claude-haiku-4-5-20251001`（轻量省钱）、`claude-sonnet-4-5`（均衡）、`claude-opus-4-5`（深度推理）

**4. env（环境变量注入）**

```json
{
  "env": {
    "NODE_ENV": "development",
    "API_BASE_URL": "http://localhost:3000",
    "LOG_LEVEL": "debug"
  }
}
```

- `env` 里的键值对会被注入到 Claude Code 运行的环境中
- Hook 里的 shell 脚本也能读取这些变量
- **安全提醒**：密钥、token 等敏感值不要写进提交 Git 的配置文件，放到 `settings.local.json` 里

#### task-manager 完整配置示例

以下是一个团队共享配置的参考结构（字段和格式是准确的，具体值根据你的项目调整）：

```json
{
  "permissions": {
    "allowedTools": [
      "Bash(npm run test)",
      "Bash(npm run test:watch)",
      "Bash(npm run build)",
      "Bash(npm run lint)",
      "Bash(npm run lint:fix)",
      "Bash(git status)",
      "Bash(git diff)",
      "Bash(git log --oneline -10)"
    ],
    "disallowedTools": []
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          {
            "type": "command",
            "command": "prettier --write \"$CLAUDE_FILE_PATHS\" 2>/dev/null || true"
          }
        ]
      }
    ]
  },
  "env": {
    "NODE_ENV": "development"
  }
}
```

```json
{
  "model": "claude-haiku-4-5-20251001",
  "env": {
    "LOG_LEVEL": "debug"
  }
}
```

（第二个 JSON 是 `settings.local.json` 的内容——个人本地，不提交 Git）

### 5.6 Git 策略

> 问题：`.claude/` 目录下那么多文件，哪些该提交，哪些不该提交？
> 心智模型：忽略文件是最后防线

#### 动手：检查 .gitignore

让 Claude 检查并修复 `.gitignore`：

```
> 检查项目根目录的 .gitignore，确认以下文件是否被正确处理：
  1. .claude/settings.local.json 应该被 ignore（不提交）
  2. .claude/settings.json 应该被提交（不在 ignore 里）
  如果 settings.local.json 没有被 ignore，帮我添加进去。
```

#### 观察：Claude 的检查结果

Claude 大致会执行以下操作：

1. 读取 `.gitignore` 文件内容
2. 检查是否有 `settings.local.json` 相关条目
3. 如果缺失，在 `.gitignore` 里添加类似 `.claude/settings.local.json` 的条目

#### 理论：.claude/ 目录的 Git 策略全览

```
task-manager/
├── CLAUDE.md                  ✅ 提交（团队规范，AI 行为指令）
└── .claude/
    ├── settings.json          ✅ 提交（团队共享配置，Hook、权限等）
    ├── settings.local.json    ❌ 不提交（个人本地配置，gitignore）
    ├── skills/                ✅ 提交（团队共享的 Skill 定义）
    │   └── add-feature/
    │       └── SKILL.md
    └── agents/                ✅ 提交（团队共享的 Agent 定义）
        └── security-reviewer.md
```

**.gitignore 推荐写法**：

```
# Claude Code 本地配置（个人私有，不共享）
.claude/settings.local.json
```

#### 动手：验证 Git 状态

让 Claude 确认配置文件的 Git 状态符合预期：

```
> 运行 git status，确认 .claude/settings.local.json
  出现在 untracked 或 ignored 里，
  而 .claude/settings.json 出现在已追踪（tracked）的文件里。
```

#### 理论：为什么 settings.local.json 必须 gitignore？

几个常见的"没 ignore 导致的问题"：

1. **暴露个人信息**：你把本地数据库密码或 API key 写进了 local 配置，一提交就泄露了
2. **团队冲突**：每个人都有自己的 local 覆盖（比如不同的模型），提交后互相干扰
3. **破坏他人环境**：你本地用 haiku 省 token，提交后团队成员拉下来也变成 haiku，可能不符合他们的需求

**默认行为提醒**：Claude Code 本身会建议将 `settings.local.json` 加入 `.gitignore`，但不会强制执行。养成手动检查的习惯。

### 6.1 Plugin vs 散装配置

> 问题：把文件提交 Git 不就行了，为什么需要 Plugin？
> 心智模型：命名空间隔离 + 依赖管理

#### 动手：感受命名冲突

在终端运行以下命令，查看当前项目的 `.claude/` 目录结构：

```bash
find task-manager/.claude -type f | sort
```

观察：如果你同时维护两个项目，都有 `add-feature` Skill，文件名会冲突。Plugin 通过目录前缀解决这个问题——`task-tools:add-feature` 和 `frontend-tools:add-feature` 可以共存。

#### 理论：散装配置的问题

目前你的工具是这样分布的：

```
task-manager/
├── .claude/
│   ├── skills/
│   │   └── add-feature/
│   │       └── SKILL.md
│   ├── agents/
│   │   └── security-reviewer.md
│   └── settings.json          ← Hook 在这里
└── CLAUDE.md
```

散装配置有三个问题：

1. **命名冲突**：如果你有两套工具，都叫 `add-feature`，谁覆盖谁？
2. **版本混乱**：工具升级了，哪些项目用的是旧版本？
3. **分发困难**：新同事需要知道哪些文件要复制、哪些不要复制

#### 理论：Plugin 解决什么

Plugin 是一个有清晰边界的工具集合。加载后，里面的 Skill 会带上 Plugin 名作为前缀：

| 散装模式 | Plugin 模式 |
|----------|-------------|
| `/add-feature` | `/task-tools:add-feature` |
| `security-reviewer` Agent | `task-tools/security-reviewer` Agent |
| 直接改 settings.json | Hook 打包在 Plugin 内部 |

命名空间前缀的好处：公司里有 `frontend-tools:add-feature` 和 `backend-tools:add-feature`，两套工具共存不冲突。

#### 理论：Plugin 的加载方式（目前最可靠）

有两种方式让团队使用 Plugin：

**方式 A（推荐）：直接提交 Git**

把 `.claude/` 目录完整提交到 Git 仓库。团队成员 clone 仓库后，Skill/Agent 立即可用，无需额外操作。这是 CC 2.1.x 中最稳定的分发方式。

**方式 B（实验性）：独立 Plugin 目录 + CLI 加载**

把 Plugin 放在独立目录，通过 `--plugin-dir` 参数加载。适合跨项目复用工具集。

> 注意：`claude --plugin-dir` 这个 CLI 参数在 CC 2.1.x 中属于实验性功能，以实际安装的版本为准。如果命令不生效，请回退到方式 A。

```bash
# check-dangerous.sh — 拦截高危命令
# 与 Ch4 版本相同，使用 stdin 读取 Hook 输入

INPUT=$(cat)
COMMAND=$(echo "$INPUT" | python3 -c "
import json, sys
data = json.load(sys.stdin)
print(data.get('tool_input', {}).get('command', ''))
" 2>/dev/null || echo "")

DANGEROUS_PATTERNS="rm -rf|DROP TABLE|DELETE FROM|format [A-Z]:|mkfs"

if echo "$COMMAND" | grep -qiE "$DANGEROUS_PATTERNS"; then
  echo "⚠️  拦截高危命令：$COMMAND" >&2
  echo "请在 Claude 对话中确认后手动执行。" >&2
  exit 2
fi

exit 0
```

#### Q&A

**Q1：Plugin 目录必须叫 `task-tools` 吗？**

目录名决定 Plugin 名（即命名空间前缀）。你可以叫任何名字，例如 `my-team-tools`，调用时就变成 `/my-team-tools:add-feature`。命名建议用全小写 + 连字符，避免空格和特殊字符。

**Q2：如果我既有 `.claude/skills/add-feature`，又有 `task-tools/skills/add-feature`，会冲突吗？**

两者命令名称不同（`/add-feature` vs `/task-tools:add-feature`），不会冲突，可以共存。迁移完成后建议删除 `.claude/skills/` 中的原始文件，保持目录整洁，避免维护两份副本。

**Q3：plugin.json 可以声明 Plugin 之间的依赖关系吗？**

CC 2.1.x 中 `plugin.json` 的依赖声明机制尚未完全稳定，以官方文档为准。目前阶段建议把所有工具打包在同一个 Plugin 内，而不是拆分成多个相互依赖的 Plugin。

**Q4：Hook 脚本放在 Plugin 里之后，settings.json 里的路径需要更新吗？**

需要。如果 Hook 脚本从 `.claude/hooks/check-dangerous.sh` 迁移到了 `task-tools/hooks/check-dangerous.sh`，`.claude/settings.json` 中引用的路径也要同步更新。迁移后运行一次验证，确认 Hook 仍然触发。

### 7.1 规范驱动开发的价值

#### 理论：口头描述 vs 结构化规范

**方式 A — 口头描述（我们之前的做法）**

```
> 给任务管理系统加一个看板视图，按状态分成三列，支持拖拽。
```

这个提示词的问题："看板视图"具体什么样、每列显示哪些字段、拖拽后调用哪个 API、验收标准是什么 — 全都没说。Claude 会尽力猜测，但两个人发同一段提示词，可能得到完全不同的实现。

**方式 B — 结构化规范（今天的做法）**

```markdown
## 功能描述
用户可以按状态（待办 / 进行中 / 已完成）分组查看所有任务，支持拖拽更改状态。

## 验收标准
- [ ] 三列看板布局（待办 / 进行中 / 已完成）
- [ ] 每列显示对应状态的任务卡片
- [ ] 任务卡片显示标题、优先级、截止日期
- [ ] 拖拽任务到其他列，调用 PATCH /tasks/:id 更新状态

## 技术约束
- 使用现有的任务 API，不新增字段
- 不引入新的重量级拖拽库（优先用原生 Drag API）
```

规范文档的优势：

| 维度 | 口头描述 | 结构化规范 |
|------|----------|------------|
| 验收标准 | 靠人记忆 | 写在文档里，逐条核对 |
| 可重现性 | 不同人得到不同结果 | Claude 每次读同一份规范 |
| 团队协作 | PM 和开发各自理解不同 | 规范是共识文档，共同签字 |
| 版本追踪 | 聊天记录散落各处 | Git 管理，可以看修改历史 |

这就是 Spec-Driven Development 的核心价值：**在给 AI 写代码之前，先把"做什么"写清楚**。

> **类比**：口头提示词就像口头给施工队交待需求——每个人听到的不一样，最后盖出来的房子形态各异。Spec-Kit 的规范文档就像正式的建筑图纸——无论谁施工，按图纸来的结果都一样，而且出了问题可以追责到具体的图纸条款。

**动手**：
1. 在 Claude Code 中输入一个模糊需求（例如"帮我做一个任务列表"），观察 Claude 的回答方式。
2. 再输入同样的需求但加上约束（例如"帮我实现一个任务列表，要求：用 React 组件，数据用 localStorage，样式用 Tailwind"），对比两次回答的差异。

**观察**：第二次回答会更具体、更接近可执行代码，因为你把"模糊意图"变成了"结构化约束"。这就是规范驱动开发的核心价值。

### 7.2 Spec-Kit 介绍与安装

#### 理论：Spec-Kit 是什么？

Spec-Kit 是 GitHub 官方发布的规范驱动开发工具包（GitHub 仓库：`github/spec-kit`）。

Spec-Kit 定义了五步开发流程：

```
constitution（原则）→ specify（需求规范）→ plan（实现计划）→ tasks（任务拆分）→ implement（实现代码）
```

| 步骤 | 命令 | 文档 | 作用 |
|------|------|------|------|
| constitution | `/speckit.constitution` | `constitution.md` | 定义项目原则，告诉 AI "什么不能做" |
| specify | `/speckit.specify` | `spec.md` | 交互式生成功能需求和验收标准 |
| plan | `/speckit.plan` | `plan.md` | AI 生成实现计划（架构、文件、接口） |
| tasks | `/speckit.tasks` | `tasks.md` | AI 把计划拆成可执行的子任务 |
| implement | `/speckit.implement` | 代码 | AI 按任务逐条实现 |

#### 动手：安装 Spec-Kit

> **以官方仓库 [github/spec-kit](https://github.com/github/spec-kit) 的最新文档为准，以下命令基于当前已知版本。**

Spec-Kit 通过官方 CLI 工具 `specify-cli` 来初始化项目。安装步骤大致如下：

> **注意**：以下安装命令以课程编写时（2025 年）验证的版本为准。Spec-Kit 框架会持续更新，部分命令的触发方式可能有所不同，但核心思想不变。具体指令的触发方式以 [GitHub 仓库](https://github.com/github/spec-kit) 的最新说明文档为准。

> **前置条件**：Spec-Kit 依赖 `uv`（Python 包管理器）。
>
> ```bash
> # macOS/Linux
> curl -LsSf https://astral.sh/uv/install.sh | sh
> # Windows（PowerShell）
> powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
> # 验证安装
> uv --version
> ```

```bash
# 第 1 步：通过 uv 安装 specify-cli（Python 工具，需要 uv 已安装）
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git

# 第 2 步：在 task-manager 项目目录内初始化（在项目根目录下执行）
specify init .

# 第 3 步：验证环境是否就绪
specify check
```

执行 `specify init` 后，项目根目录会出现**类似**这样的目录结构（以实际 `specify init` 执行后的输出为准）：


### 7.3 动手：用 Spec-Kit 实现看板视图（US-6）

#### 动手：第一步 — 安装 Spec-Kit 并初始化项目

> **前提**：已完成 7.2 节的安装步骤（`specify init` 和 `specify check`）。如尚未安装，先回到 7.2 节执行安装命令（以官方仓库版本为准）。

安装完成后，可选择运行 `/speckit.constitution`（以官方仓库版本为准）建立项目原则：

```
/speckit.constitution
```

输入该命令后，Claude Code 会引导你描述项目的核心原则（例如：禁止引入新的重量级依赖、所有新组件需与现有风格一致、不得新增数据库字段等），并将原则写入**类似** `.specify/memory/constitution.md` 的文件。

生成的 `constitution.md` 内容大致如下：

```markdown
# Project Constitution: task-manager

## Principles

### P1: No New Heavy Dependencies
- MUST NOT introduce ORM frameworks (Prisma, TypeORM, etc.)
- MUST use existing lightweight database access patterns

### P2: Consistent Component Style
- All new React components MUST follow existing naming conventions
- MUST NOT introduce CSS-in-JS if project uses Tailwind

### P3: Database Schema Stability
- MUST NOT add new database columns or tables for this feature
- MUST reuse existing API endpoints where possible

## Version
- Version: 1.0.0
- Last Updated: [日期]
```

> 这些原则会被后续的 `/speckit.plan` 和 `/speckit.analyze` 自动引用，违反 MUST 原则的方案会被标记为 CRITICAL。

> **constitution 是可选步骤**：如果这是第一次在 task-manager 上使用 Spec-Kit，建议先跑一次 `/speckit.constitution`，它能帮后续所有命令自动遵守项目约束，省去在每次提示词中重复声明。如果项目约束已在 CLAUDE.md 中写明，也可跳过此步，直接进入第二步。

#### 动手：第二步 — 用 `/speckit.specify` 生成规范

Spec-Kit 的规范文件**不是手工写的**，而是通过 `/speckit.specify` 命令（以官方仓库版本为准）与 AI 交互生成的。

在 Claude Code 对话中输入（命令后跟简短的需求描述）：

```
/speckit.specify 为 task-manager 添加看板视图功能（US-6）
```

Claude Code 会读取 `/speckit.specify` 命令的模板，**交互式地询问细节**——例如：验收标准是否完整、边界情况如何处理、有哪些不在本次范围内。在交互问答中补充约束：使用现有 PATCH /tasks/:id 接口、不新增数据库字段、优先用浏览器原生 Drag and Drop API。回答完毕后，Claude 会自动生成**类似**这样的规范文件：

```
.specify/specs/002-kanban-view/spec.md
```

生成的 `spec.md` 内容大致包含：

```markdown
# 功能规范：看板视图（US-6）

## 用户故事
作为 PM，我想按状态分组查看任务，支持看板视图。

## 验收标准
- [ ] 页面顶部有"列表视图 / 看板视图"切换按钮
- [ ] 看板视图分三列，每列显示任务数量
- [ ] 每张任务卡片显示标题、优先级标签、截止日期
- [ ] 点击卡片可查看任务详情
- [ ] 任务卡片可在列之间拖拽并更新状态
- [ ] 拖拽失败时显示错误提示，卡片回到原位

## 技术约束
- 使用现有的任务 API，不新增数据库字段
- 前端组件风格与现有代码一致
- 优先使用浏览器原生 Drag and Drop API
- 不引入新的重量级依赖

## 不在本次范围内
- 列内排序（卡片上下拖拽调整顺序）
- 看板视图的筛选和搜索
```

> 心智模型：动词加主语加结果

#### 动手：第二步半 — 澄清模糊点（可选）

spec.md 生成后，某些描述可能仍然模糊。在进入 plan 之前，可以用 `/speckit.clarify` 清理模糊点：

**问题**：spec.md 生成后，某些描述仍然模糊（比如"系统应该快速响应"），如何在进入实现之前把模糊点清理掉？

**动手**

1. 在完成第二步（`/speckit.specify`）并生成 spec.md 后，运行（以官方仓库版本为准）：

```
/speckit.clarify
```

2. Spec-Kit 会从 10 个维度扫描 spec.md 中的模糊点，然后**每次只问你一个问题**，大致格式如下：

```
问题 1/3：关于"拖拽失败"的定义

  推荐选项（Recommended）：
    A. 网络请求失败（HTTP 非 2xx）时视为拖拽失败

  选项表格：
  | 选项 | 说明 |
  |------|------|
  | A    | 网络请求失败时回退 |
  | B    | 任何客户端异常也视为失败 |
  | C    | 自定义回答... |

  请输入字母、"yes" 接受推荐，或直接描述你的答案：
```

3. 输入你的选择（如 `A` 或 `yes`），Spec-Kit 会立即将答案写入 spec.md，然后问下一个问题。

4. 回答完毕（或在任意时刻输入 `done`）后，打开 spec.md，查看 `## Clarifications` 章节，确认你的回答已记录在案。

**观察**

你会看到**类似**这样的变化：

- spec.md 顶部或末尾新增了 `## Clarifications` 章节，按日期记录每条澄清问答
- spec.md 正文中原来模糊的描述（如"快速响应"）被替换为具体量化内容（如"接口响应不超过 500ms"），不会留下前后矛盾的旧文本
- 命令最多提 5 个问题，整个会话最多 10 个

**理论**

clarify 按以下 10 个维度扫描规范，优先问"答案会实质影响架构、数据建模、任务拆分或测试设计"的问题：

| 维度 | 扫描内容 |
|------|---------|
| 功能范围 | 核心目标、明确排除项 |
| 数据模型 | 实体、属性、关系定义 |
| 交互流程 | 用户旅程、空状态、错误状态 |
| 非功能属性 | 性能、可用性的量化指标 |
| 集成依赖 | 外部服务、失败模式 |
| 边界情况 | 负面场景、并发冲突 |
| 约束权衡 | 技术约束、被拒方案 |
| 术语一致性 | 规范术语、废弃同义词 |
| 完成信号 | 验收标准是否可测试 |
| 杂项占位符 | TODO、模糊形容词 |

> 使用时机：spec.md 生成后，进入 `/speckit.plan` 之前。尤其当你对某个边界情况有疑问时，先用 clarify 澄清，比让 plan 带着模糊点往下走要省事得多。

生成的 `tasks.md` 内容大致包含分阶段的任务清单，例如：

```
## Phase 2: User Story 1 - 看板展示 (Priority: P1)

## Phase 3: User Story 2 - 拖拽交互 (Priority: P2)
- [ ] T005 [US2] 封装拖拽逻辑
```

#### 动手：第五步 — 分步实现代码

拿到 plan.md（和可选的 tasks.md）后，不要一次性让 Claude 实现全部内容。有两种方式推进：

**方式 A：使用 `/speckit.implement` 自动驱动**（推荐）

```
/speckit.implement
```

Spec-Kit 会读取 tasks.md，按任务顺序逐条驱动 Claude 实现。每完成一个任务，自动勾选 `[X]` 并进入下一个。适合单人开发、想要全自动执行的场景。

**方式 B：手动分步推进**

如果你想对每一步有更多控制（比如中途审查、调整方案），可以不用 `/speckit.implement`，而是手动给 Claude 下达指令，每步确认后再继续：

---

**第 5a 步：创建骨架结构**

输入：
```
按 plan.md 第 1 步，创建看板视图的骨架组件。
只需要布局结构（三列：待办 / 进行中 / 已完成），
不需要实现交互和数据加载，
完成后告诉我创建或修改了哪些文件。
```

观察：Claude 创建相关文件并列出清单，你能在浏览器中看到三列的静态布局（列标题和空白区域），页面不报错。

---

**第 5b 步：接入真实数据**

输入：
```
现在按 plan.md 第 2 步，把真实数据加载到看板视图中。
调用现有的获取列表接口，按状态分组显示到对应列，
完成后告诉我数据从哪个接口拉取、按什么字段分组。
```

观察：三列中出现数据卡片，每张卡片显示标题和关键字段（大致如名称、优先级等），列标题旁有数量统计。

---

**第 5c 步：实现状态更新交互**

输入：
```
按 plan.md 第 3 步，实现状态更新的交互。
调用现有的更新接口，在用户操作（拖拽或点击）后更新状态。
实现后描述一下：用户完成一次操作到数据持久化，
经过了哪些步骤。
```

观察：执行一次状态变更操作后，卡片移到对应列；刷新页面后状态保持，说明数据已写回后端。

**第 5d 步：补充测试**

输入：
```
按 plan.md 最后一步，为新增的核心逻辑编写测试。
覆盖：数据按状态分组是否正确、
状态更新接口调用是否带正确参数。
```

观察：测试文件创建完毕。如果不确定测试命令，问 Claude：“这个项目用什么命令运行所有测试？”——Claude 会根据 package.json 中的 scripts 告诉你（通常是 `npm test` 或 `npx vitest`）。确认全部通过，无报错。

> **中途卡住怎么办？** 如果 Claude 偏离了 plan.md 的步骤、自行引入计划外的文件或依赖，可以说："先暂停。请重新读一下看板视图的 plan.md，告诉我当前应该在哪一步，然后从那步继续实现，不要修改计划范围之外的内容。"

#### 动手：第六步 — 用规范文档验收

Spec-Kit 没有专门的"验收"命令。验收的方式是让 Claude 对照 spec.md 的验收标准逐条核对——这正是规范文档的价值：**验收标准在 specify 阶段就已经写好了，不需要额外的命令来生成**。

如果你想更严格地验收，可以先运行 `/speckit.analyze`（交叉验证 spec/plan/tasks 的一致性），再手动让 Claude 对照 spec.md 检查实现：

```
实现完成了。请对照看板视图的 spec.md 中的验收标准逐条检查，
列出已通过 / 未通过的项，对未通过的给出修复方案。
```

Claude 会输出一份核对清单，**类似**这样：

```
⏺ 验收标准核对结果：

  ✅ 页面顶部有"列表视图 / 看板视图"切换按钮
  ✅ 看板视图分三列，每列有标题和数量统计
  ✅ 任务卡片显示标题、优先级、截止日期
  ✅ 拖拽后调用更新接口修改状态
  ❌ 拖拽失败时未显示错误提示（待修复）

  我来修复错误处理部分...
```

这就是"规范驱动"验收的完整闭环：**规范定义成功标准 → AI 实现 → AI 自查 → 人工确认**。

#### 观察：和口头提示词相比有什么不同？

| 环节 | 口头提示词 | Spec-Kit 规范驱动 |
|------|------------|-----------------|
| 需求输入 | 一段话，信息不完整 | spec.md，结构化，逐条列出 |
| 实现计划 | Claude 自己决定 | plan.md，人工审核后再执行 |
| 验收方式 | 看看"感觉对不对" | 对照 spec.md 逐条核对 |
| 可追溯性 | 聊天记录 | Git 管理的文档 |

#### 7.3.8 质量治理三件套

质量治理三件套（constitution、checklist、analyze）覆盖从"定规则"到"查一致性"的完整链路，彼此协同但各有侧重：

```
constitution（定规则）
    → plan gate（方案合规检查）
    → analyze（交叉验证）
    → checklist → implement gate（实现前门禁）
```

##### constitution — 项目基本法

> 问题：团队里有多人协作，怎么让所有人遵守同一套规则？
> 心智模型：团队共识，一纸约定

**动手**

1. 在 Claude Code 中运行（以官方仓库版本为准）：

```
/speckit.constitution
```

2. 描述 task-manager 项目的核心约束，例如：

```
所有 API 端点 MUST 有错误处理，
包括参数校验失败、资源不存在、服务器内部错误
三种情况的标准响应格式。
不得新增数据库字段，已有字段必须向后兼容。
```

3. 命令执行完成后，查看生成的文件（大致位于 `.specify/memory/constitution.md`），确认原则已写入。

**观察**

你会看到**类似**这样的变化：

- 文件顶部有一段 HTML 注释格式的 Sync Impact Report，记录版本变更（如 `1.0.0 → 1.1.0`）和受影响的模板列表
- 正文中原则使用 `MUST` / `MUST NOT` 强制语言，例如：`所有 API 端点 MUST 包含错误处理`
- 文件底部有版本号和最后修订日期

**理论**

constitution 对其他命令有实际约束力，不是普通文档：

| 命令 | constitution 的作用 |
|------|-------------------|
| `/speckit.plan` | Phase 0 前 + Phase 1 后各做一次合规检查 |
| `/speckit.analyze` | 违反 MUST 原则的发现自动升级为 CRITICAL |

版本管理遵循语义化版本：原则增删为 MAJOR，内容实质扩展为 MINOR，措辞澄清为 PATCH。原则使用 MUST / MUST NOT 强制语言，SHOULD 为建议，MAY 为可选（不检查）。

> 类比：constitution 就像团队的"基本法"。plan 生成技术方案时必须通过合宪审查，analyze 检查文档时把违宪问题列为最高严重级别。

##### checklist — 需求质量门禁

> 问题：spec.md 写完了，怎么确认需求本身没有遗漏？
> 心智模型：需求的单元测试

**动手**

1. 在 Claude Code 中运行（以官方仓库版本为准）：

```
/speckit.checklist
```

2. Spec-Kit 会先问最多 3 个澄清问题来确定焦点（如检查深度、关注维度），例如：

```
你希望这次 checklist 聚焦在哪个维度？
  A. API 层需求完整性
  B. 前端交互边界情况
  C. 全面覆盖（所有维度）
```

3. 回答后等待生成。生成完毕后，查看新增的 checklist 文件（大致位于 `specs/.../checklists/` 目录下）。

**观察**

你会看到**类似**这样的结果：

- 在 `checklists/` 目录下生成了一个新文件（如 `api.md` 或 `ux.md`）
- 每个条目的格式大致为：`- [ ] CHK001 Are error handling requirements defined... [Completeness, Spec §3.2]`
- 所有条目都在问"需求写得好不好"，而不是"功能做得对不对"
- 不会出现"Verify the button clicks correctly"这类实现测试项

**理论**

checklist 的核心理念：**"Unit Tests for English"**——它是需求文档的单元测试，不是功能的测试套件。

| 维度 | 错误做法 | 正确做法 |
|------|---------|---------|
| 测试对象 | 实现行为 | 需求文本 |
| 典型动词 | Verify / Test | Are... defined? |
| 关注点 | 功能是否正常 | 需求是否完整清晰 |

`/speckit.implement` 执行前会扫描 `checklists/` 目录：全部通过则自动进入实现；有未通过项则停下来询问是否继续。这是 checklist 的"门禁"效果。

---

##### analyze — 跨文档交叉验证

> 问题：spec、plan、tasks 三份文档之间会不会自相矛盾？
> 心智模型：三份文档，交叉验证

**动手**

1. 确保 spec.md、plan.md、tasks.md 都已生成（analyze 需要三份文档同时存在）。

2. 运行（以官方仓库版本为准）：

```
/speckit.analyze
```

3. 等待分析完成，阅读输出的结构化报告。

**观察**

你会看到**类似**这样的结果：

- 命令不会修改任何文件（严格只读）
- 输出一份 Markdown 报告，大致包含：
  - 发现表格：ID、Category、Severity、Location、Summary、Recommendation
  - Coverage Summary：每条需求是否有对应任务
  - Constitution Alignment Issues：如果有违规
  - Metrics 汇总：总需求数、覆盖率、歧义数等

```
Total Findings: 5
  CRITICAL: 1  （违反 MUST 原则）
  HIGH:     2  （需求无对应任务）
  MEDIUM:   1  （术语漂移）
  LOW:      1  （措辞冗余）
Coverage: spec → tasks 85%
```

- 如果存在 CRITICAL 问题，报告末尾会建议在 implement 之前先修复

**理论**

analyze 的 6 个检测维度：

| # | 维度 | 示例 |
|---|------|------|
| 1 | 重复 | 两条需求描述同一功能 |
| 2 | 歧义 | "快速"、"安全"缺乏量化 |
| 3 | 不足 | 有动词但无验收标准 |
| 4 | Constitution 对齐 | 违反 MUST 原则 |
| 5 | 覆盖缺口 | spec 有需求但 tasks 无任务 |
| 6 | 不一致 | plan 叫"Task"，spec 叫"Todo" |

严重性分级：

| 级别 | 触发条件 |
|------|---------|
| CRITICAL | 违反 constitution MUST 原则 |
| HIGH | 需求冲突、安全属性模糊 |
| MEDIUM | 术语漂移、非功能需求无覆盖 |
| LOW | 措辞风格、轻微冗余 |

> 关键原则：analyze 严格只读，绝不修改任何文件。它只报告问题，由团队决定如何处理。Constitution 违规不可降级——MUST 冲突永远是 CRITICAL。

> 使用时机：plan 完成后运行一次，implement 开始前再运行一次，作为"开工前检查"。

#### 7.3.9 任务变工单：`/speckit.taskstoissues`

> 问题：tasks.md 里有几十个任务，怎么分配给团队成员？
> 心智模型：任务变工单，分工协作

**动手**

1. 确认两个前置条件都已满足：

```bash
# 确认 tasks.md 已存在
ls .specify/specs/002-kanban-view/tasks.md

# 确认项目有 GitHub remote
git config --get remote.origin.url
```

2. 如果 remote URL 是 GitHub 地址（`github.com` 开头），在 Claude Code 中运行（以官方仓库版本为准）：

```
/speckit.taskstoissues
```

3. 观察命令逐个创建 Issue 的过程，每个 Issue 对应 tasks.md 中的一个任务。

**观察**

配置好 GitHub MCP 后，你会看到**类似**这样的过程：

- 命令先核对前置条件：tasks.md 是否存在，remote 是否为 GitHub URL
- 如果 remote 不是 GitHub URL（比如 GitLab 或 Bitbucket），命令会**直接停止**，不尝试创建任何内容
- 逐个调用 GitHub MCP server 创建 Issue，每个 Issue 大致包含：
  - 标题：Task ID + 描述（如 `T005 [US2] 封装拖拽逻辑`）
  - 标签：User Story 编号（如 `US2`）
  - 正文：依赖关系引用
- 打开 GitHub 仓库的 Issues 页面，可以看到按 User Story 标签分类的任务列表

**理论**

taskstoissues 的映射规则：

| tasks.md 元素 | GitHub Issue 字段 |
|--------------|------------------|
| Task ID + 描述 | Issue 标题 |
| `[USn]` 标签 | Issue label |
| 依赖关系 | Issue body 中引用 |
| Phase 信息 | Issue 分组上下文 |

命令内置了两条安全限制（以官方仓库版本为准）：只在 remote 为 GitHub URL 时执行；绝不在与 remote 不匹配的仓库中创建 Issues。这防止误操作到其他人的项目。

使用 GitHub MCP server（`github/github-mcp-server/issue_write`）与 GitHub API 交互，而不是直接调用 `gh` CLI——这是 Spec-Kit 中唯一声明了外部工具依赖的命令，需要提前配置好 GitHub MCP server。

> **注意**：`/speckit.taskstoissues` 需要 GitHub MCP Server 才能创建 Issues。GitHub MCP 的配置步骤在 Ch8 中讲解——如果你现在跟着课程顺序学习，可以先了解这个命令的机制，等 Ch8 配置好 MCP 后再实际执行它。

> 这一步的价值：tasks.md 按 User Story 组织的结构，让 Issues 天然适合按故事分配给不同人。团队成员可以直接在 GitHub Issues 里认领任务、更新进度，不需要维护单独的看板。

#### 7.3.10 团队协作分工

**问题**：一个人跑通全链路没问题，但团队里有 Tech Lead、架构师、开发者、QA、PM——每个人该用哪些命令？文档怎么在角色之间流转？

**动手**

以 task-manager 项目的看板视图功能为例，模拟一次三人团队协作：

1. **Tech Lead（小张）**：运行 `specify → plan → tasks`，产出需求、方案、任务三份文档
2. **QA（小李）**：拿到文档后运行 `analyze`，确认 spec/plan/tasks 之间无遗漏和矛盾；运行 `checklist` 生成需求质量检查清单
3. **开发者（小王）**：查看 tasks.md，认领带 `[P]` 标记的前端任务，运行 `implement` 或按 tasks.md 手动实现
4. **PM（小陈）**：运行 `taskstoissues`，将未完成任务同步到 GitHub Issues 并分配给团队成员
5. **架构师（老孙）**：维护 `constitution.md`，在有新的架构约束时运行 `/speckit.constitution` 更新

**观察**

运行完上述协作流程后，你会看到**类似**这样的分工效果：

- tasks.md 中 `[P]` 标记的任务，前端和后端开发者可以同时开工，互不阻塞
- `[US1]`/`[US2]` 标签让每个 User Story 可以整体分配给一个人或小组
- Phase 结构提供了天然的同步点：Foundational 阶段完成后，所有 User Story 才能并行推进

**理论**

团队角色与命令映射：

| 角色 | 主要命令 | 主要产出 |
|------|---------|---------|
| Tech Lead | specify, clarify, tasks | 需求文档、任务清单 |
| 架构师 | plan, constitution | 技术方案、项目原则 |
| 开发者 | implement | 代码实现 |
| QA | analyze, checklist | 质量报告、需求检查清单 |
| PM | taskstoissues | GitHub Issues |

并行分工有三个粒度可以选择：

| 粒度 | 依据 | 适用场景 |
|------|------|---------|
| 最细 | `[P]` 标记 | 同一阶段内并行任务 |
| 推荐 | `[US]` 标签 | 每个 User Story 分给一人/小组 |
| 最粗 | Phase 阶段 | Foundational 组 + Stories 组 |

文档流转路径：

```
Tech Lead: specify → spec.md
               plan → plan.md + data-model.md
               tasks → tasks.md
                  |
                  ├─ QA: analyze → 质量报告
                  ├─ QA: checklist → 需求检查清单
                  ├─ 开发者: implement → 代码
                  └─ PM: taskstoissues → GitHub Issues
```

> 注意：开发者在团队场景中不一定需要运行 `implement`，也可以直接按 tasks.md 手动编码，完成后勾选 `[X]`。`implement` 更适合单人全自动执行的场景。
>
> **部分执行**：`/speckit.implement` 支持只执行选定的任务（以官方仓库版本为准）。与手动指挥 Claude 编码的区别在于：`implement` 会自动读取 spec.md + plan.md + constitution.md 作为上下文约束，确保实现不偏离规范；手动编码时你需要自己提醒 Claude 参考这些文档。简单来说——`implement` 是"带护栏的自动驾驶"，手动编码是"自己开车但更灵活"。

#### 观察：Spec-Kit 9 个命令全景

| 命令 | 前置条件 | 主要产出 | 谁来用 |
|------|---------|---------|-------|
| specify | 无 | spec.md | Tech Lead |
| clarify | spec.md | 更新的 spec.md | Tech Lead |
| plan | spec + constitution | plan.md 等 | 架构师 |
| tasks | plan + spec | tasks.md | Tech Lead |
| checklist | spec.md | checklists/*.md | QA |
| analyze | spec+plan+tasks | 分析报告 | QA |
| implement | tasks + plan | 代码实现 | 开发者 |
| taskstoissues | tasks + GitHub | GitHub Issues | PM |
| constitution | 无（首次） | constitution.md | 架构师 |

### 7.4 BMAD-Method：企业级全生命周期开发框架

如果说 Spec-Kit 解决的是"功能级规范"，BMAD-Method（Breakthrough Method for Agile AI Driven Development）解决的是"**项目级全生命周期**"——从需求分析、产品规划、系统架构，一直到代码实现和质量验收。

#### 理论：BMAD 是什么

核心理念：**AI 不只是代码生成器，而是能扮演多个专家角色的协作团队**。

```
传统模式：                          BMAD 模式：

  开发者                              开发者
    │                                   │
    ▼                                   ▼
┌─────────┐                     ┌───────────────┐
│  AI     │                     │  AI 专家团队   │
│ (代码   │                     │               │
│  生成器) │                     │  Mary 分析师   │
└────┬────┘                     │  John PM      │
     │                          │  Winston 架构  │
     ▼                          │  Amelia 开发   │
   代码                         │  Quinn QA     │
                                │  Paige 文档   │
                                │  Barry 极速流  │
                                └───────┬───────┘
                                        │
                                        ▼
                                  完整交付物
                                (PRD+架构+代码+测试+文档)
```

通过 Claude Code 的 slash command，你可以随时召唤对应角色，让它以该领域专家的方式思考和产出。

**安装**（以官方文档 docs.bmad-method.org 为准）：

> **前置条件**：需要 Node.js 18+。运行 `node -v` 确认版本。
> 安装过程是交互式向导（约 2-5 分钟），遇到选项时：集成工具选 Claude Code，输出语言选中文。

```bash
npx bmad-method install
```

这是一个交互式 CLI 向导，安装过程中会询问：安装目录、模块选择（BMad Method Agile-AI）、集成工具（选 Claude Code）、输出语言（中文）等。

安装完成后，项目中自动生成：

- `_bmad/`：核心文件（agents、workflows、tasks 定义）
- `_bmad-output/`：产出物目录（`planning-artifacts/`、`implementation-artifacts/`）
- `.claude/skills/`：工作流 slash command（自动安装到 Claude Code，以官方文档实际安装路径为准）

**安装验证**：安装完成后，在终端运行以下命令确认关键目录和文件存在：

```bash
ls _bmad/ _bmad-output/ .claude/skills/ 2>/dev/null || echo "目录不存在，请检查安装步骤"
```

你应该看到 `_bmad/`、`_bmad-output/`、`.claude/skills/` 三个目录都有内容。如果缺少任意一个，重新运行 `npx bmad-method install` 并确认选择了"Claude Code"作为集成工具。

> **排错提示**：如果 `npx bmad-method install` 失败（网络超时或 Node 版本问题），可以临时跳过 BMAD 安装，直接阅读本节理论内容；Spec-Kit 的功能与 BMAD Quick Flow 的定位类似，中级课程的核心练习用 Spec-Kit 完成即可。

### Q&A

**Q1：Spec-Kit 的 spec.md 和 CLAUDE.md 有什么区别？**

A：两者互补，不冲突。`CLAUDE.md` 在项目根目录，定义**全局规则**（代码风格、禁止操作），每次 Claude 进入项目都会读取。`spec.md` 在 `.specify/specs/功能目录/` 下，定义**单个功能的规范**，只在处理对应功能时使用。类比：CLAUDE.md 是公司制度手册，spec.md 是某个需求的详细说明书。

**Q2：如果 Spec-Kit 的安装命令报错，怎么办？**

A：Spec-Kit 是持续演进的开源项目，安装方式和命令可能随版本更新。遇到报错时访问 https://github.com/github/spec-kit 查看最新说明。如安装遇到问题，建议先排查环境（确认 Python 和 uv 已安装，运行 `uv --version` 验证），或参考官方仓库 [github/spec-kit](https://github.com/github/spec-kit) 的 Issues 寻求帮助。Spec-Kit 的核心价值在于 `/speckit.specify` 等命令的交互式引导和质量验证循环，手动绕过命令会失去这些保障。

**Q3：BMAD-Method 适合我们 3 人小团队吗？**

A：3 人小团队建议先用 Spec-Kit 建立规范化写作的习惯。当项目规模增长（功能 > 20、团队 > 5 人）或需要完整文档链时再引入 BMAD-Method。也可以借鉴 BMAD 的"角色切换"理念，在一次对话里让 Claude 分别扮演 PM 和 Architect 角色审视需求，不一定要完整安装框架。

**Q4：规范写得太详细，反而浪费时间怎么办？**

A：规范的细化程度要和功能复杂度匹配。简单功能（改个按钮颜色）：口头提示词足够。中等功能（看板视图这类）：写验收标准 + 技术约束，值得投入。经验规则：**如果预计实现时间 > 4 小时，写规范文档的时间一定能回收回来**。

### 8.1 MCP 是什么？

> 问题：MCP 到底是什么？和普通 API 调用有什么区别？
> 心智模型：Claude 的 USB 接口

#### 理论：没有 MCP vs 有 MCP

**没有 MCP**：你手动调 GitHub API → 复制结果给 Claude → Claude 给建议 → 你再执行

**有了 MCP**：Claude 直接调 GitHub API → 直接处理结果 → 直接执行下一步

中间层消失了，Claude 从"顾问"变成了"执行者"。

#### 理论：两种主流传输方式

| 传输方式 | 适用场景 | 典型例子 |
|----------|----------|----------|
| `stdio` | 本地进程，最常用 | SQLite、文件系统、本地脚本 |
| `http` | 远程服务，云端 API | GitHub、Slack、远程数据库 |

> 历史上还有 SSE（Server-Sent Events）传输方式，已废弃，新项目不要使用。

#### 理论：MCP Server 提供什么

一个 MCP Server 向 Claude 暴露三类能力：

- **Tools**：Claude 可以调用的函数（"创建 Issue"、"查询数据库"）
- **Resources**：Claude 可以读取的内容（"某个文件"、"某张数据库表"）
- **Prompts**：预定义的提示模板

日常使用最常接触的是 **Tools**——Claude 自主决定何时调用哪个工具，无需你手动触发。

**动手**：
1. 在终端运行：
   ```bash
   claude mcp list
   ```
2. 观察当前已安装的 MCP Server 列表（如果没有，会显示空列表或提示未配置）。

**观察**：此时你已经看到了 MCP 的"插槽"——下一节（8.2）会往这个插槽里装入第一个 MCP Server。

### 8.2 动手：添加 GitHub MCP，Claude 直接操作 GitHub

> 问题：怎么让 Claude 直接读写我的 GitHub 仓库？
>
> 心智模型：插上授权即可操作

#### 理论：MCP 管理命令

```bash
claude mcp add <name> [options]   # 添加 MCP Server
claude mcp list                    # 列出已添加的 MCP
claude mcp get <name>             # 查看某个 MCP 详情

```

这些命令在 CC 会话**外部**（终端）运行，管理配置文件。会话**内部**用 `/mcp` 命令查看连接状态。

> **前置检查**：运行 GitHub MCP 前，确认以下条件满足：
> - Node.js 18+（`node -v`）和 npm（`npm -v`）已安装
> - 有 GitHub 账号，且项目有对应的 GitHub 远程仓库（`git remote -v`）
>
> **配置后如遇问题**：
> - 命令报错 "package not found"：先运行 `npm install -g @modelcontextprotocol/server-github`
> - Claude 提示需要认证：按照引导完成 GitHub OAuth 流程，或在 shell 中设置 `GITHUB_TOKEN` 环境变量
> - 重启 Claude Code 后运行 `/mcp` 确认连接状态

#### 动手：添加 GitHub MCP

> 以下命令以 Claude Code 2.1.x 为基准，具体参数请以**实际 CC 版本文档**为准。

```bash
# 方式一（HTTP 传输，需配置 server URL，以官方文档为准）：
# claude mcp add --transport http <server-url>

# 方式二：通过 npx 添加 stdio 传输（通用方式）
claude mcp add github-mcp --command "npx @modelcontextprotocol/server-github"
```

#### 动手：确认连接并完成认证

启动 CC 会话，输入 `/mcp` 查看连接状态：

```
MCP Servers:
  github-mcp    stdio    connected
```

如果需要访问私有仓库，Claude 会引导 OAuth 认证：

```
> 请帮我列出 github.com/[your-org]/task-manager 的 open Issues
```

Claude 返回授权链接，浏览器完成 OAuth 后告知 Claude 继续即可。

#### 动手：实现 US-7 — 从 GitHub Issues 同步任务

```
读取 GitHub 仓库 [your-org/task-manager] 中 open 状态的 Issues，
在 task-manager 数据库中为每个 Issue 创建对应的任务：
- 任务标题 = Issue 标题
```

### 8.3 动手：添加 SQLite MCP，用自然语言查数据库

### 8.4 MCP 作用域与管理命令

> 问题：我在这台电脑上加了 GitHub MCP，团队其他人要怎么用同一套配置？
>
> 心智模型：存放位置决定可见范围

#### 理论：三种作用域

| 作用域 | 存储位置 | 适用场景 |
|--------|----------|----------|
| `local`（默认） | 用户级配置目录 | 个人专用，不进 Git |
| `project` | 项目根目录 `.mcp.json` | 团队共享，提交 Git |
| `user` | 全局用户目录 | 所有项目通用 |

> **注意**：`--scope` 参数的具体名称以当前版本 `claude mcp add --help` 输出为准。

```bash
# 默认 local
claude mcp add github-mcp --command "npx @modelcontextprotocol/server-github"

# project 作用域（写入 .mcp.json，可提交 Git）
claude mcp add github-mcp --scope project --command "npx @modelcontextprotocol/server-github"
```

用 `--scope project` 添加后，项目根目录生成 `.mcp.json`：

```json
{
  "mcpServers": {
    "github-mcp": {
      "transport": "stdio",
      "command": "npx @modelcontextprotocol/server-github"
    }
  }
}
```

提交 `.mcp.json` 到 Git，团队 `git pull` 后 CC 自动识别配置。

> **安全提示**：`.mcp.json` 只存命令和传输配置，**不存** Token 或密钥。认证信息通过环境变量（如 `GITHUB_TOKEN`）传递，不进 Git。

### 8.5 Git 高级工作流（基于 GitHub MCP 创建 PR）

> 问题：功能开发完了，怎么规范地创建 PR 并走完 Code Review 流程？
>
> 心智模型：MCP 让 Claude 成 PR 助理

#### 理论：功能分支工作流

```
main（稳定主干）
  └── feature/xxx（功能分支）—— 完成后创建 PR 合并回 main
  └── fix/xxx（修复分支）
```

最佳实践：小步提交（每个 commit 只做一件事）、PR 描述清晰、Review 通过再合并。

#### 动手：创建功能分支并拆分 commit

```bash
git checkout -b feature/github-issue-sync
```

让 Claude 按功能拆分 commit：

```
我刚完成了 US-7（GitHub Issue 同步功能），
修改了 sync-service.ts、task-repository.ts、api/sync.ts 和测试文件。
帮我按功能逻辑拆分成 2-3 个 commit，遵循 feat/fix/test 前缀规范。
```

Claude 分析后给出**类似**这样的建议：

```
⏺ 建议拆分为 3 个 commit：
  feat: 添加 GitHub Issue 同步服务（sync-service.ts）
  feat: 添加任务仓库批量创建接口（task-repository.ts）
  test: 添加 Issue 同步功能测试用例
  是否按这个方案执行？
```

确认后 Claude 依次执行 `git add` 和 `git commit`。

#### 动手：通过 GitHub MCP 创建 PR

```
feature/github-issue-sync 已 push 到 origin。
请通过 GitHub MCP 在 [your-org/task-manager] 创建 PR：
- 目标分支：main
- PR 描述包含：变更内容、测试说明、关联的 Issues
- 关联 US-7 对应的 GitHub Issue
```

Claude 调用 GitHub MCP 创建 PR，返回**类似**：

```
⏺ PR 创建成功！
  标题：feat: GitHub Issue 自动同步到任务管理系统
  链接：https://github.com/your-org/task-manager/pull/42
  关联 Issue：#31（US-7）
```

#### 动手：Code Review — 用 Agent 或自然语言审查

**方式一：使用 security-reviewer Agent（需团队配置）**

```
/security-reviewer
审查 PR #42，重点关注：密钥泄露风险、SQL 注入、外部 API 错误处理。
```

**方式二：直接让 Claude 审查（无需额外安装）**

```
审查 feature/github-issue-sync 相对于 main 的所有变更，
给出 CRITICAL / HIGH / MEDIUM / LOW 四级问题列表，注明文件名和行号。
```

> `/code-review` 不是 CC 内置命令，需提前放置在 `~/.claude/skills/` 目录下才能使用。

返回**类似**的 Review 报告：

```
⏺ Code Review 报告（PR #42）

  HIGH（需修复后才能合并）：
  [H1] sync-service.ts:47 — 缺少 GitHub API 调用失败的重试逻辑
  [H2] api/sync.ts:23    — 同步接口没有鉴权

  MEDIUM（建议修复）：
  [M1] sync-service.ts:89 — Issue body 截取未处理 null 情况

  LOW（可选）：
  [L1] task-repository.ts:156 — 批量插入可用事务包裹提升性能
```

#### 动手：修复意见并更新 PR

```
请修复 H1 和 H2：
H1：在 sync-service.ts:47 添加指数退避重试（最多 3 次）
H2：在 api/sync.ts:23 添加 Bearer Token 鉴权中间件
```

修复后提交推送，PR 自动更新：

```bash
git add sync-service.ts api/sync.ts
git commit -m "fix: 添加 API 重试逻辑和同步接口鉴权"
git push origin feature/github-issue-sync
```

### 8.7 串联练习 + 小结 + Q&A

#### 动手：串联练习（15 分钟）

**目标**：为 US-7 走完从 MCP 配置到 PR 的全链路

1. **添加 MCP**（3 分钟）：添加 SQLite MCP，用 `/mcp` 确认，自然语言查"当前有多少高优先级任务"
2. **同步 Issues**（5 分钟）：用 GitHub MCP 同步 3-5 个测试仓库的 Issues，SQLite MCP 验证结果
3. **创建 PR**（4 分钟）：切出功能分支，提交变更，GitHub MCP 创建 PR 并自动生成描述
4. **Code Review**（3 分钟）：让 Claude 审查 PR，记录至少一个 MEDIUM 级别意见

> 没有真实 GitHub 仓库的学员：用 `claude mcp list` 练习管理命令，用 SQLite MCP 练习自然语言查询，PR 部分：如无真实 GitHub 仓库，可在模拟仓库上操作或跳过。

#### 小结

| 能力 | 实现方式 | 核心命令 |
|------|----------|----------|
| Claude 操作 GitHub | GitHub MCP | `claude mcp add github-mcp` |
| Claude 查询数据库 | SQLite MCP | `claude mcp add sqlite` |

**本章三条核心原则**：

1. **MCP = 外设接口**：添加什么 MCP，Claude 就能操作什么工具
2. **作用域决定共享范围**：个人用 `local`，团队用 `project`（提交 `.mcp.json`）
3. **PR 流程可以全自动**：从拆分 commit、生成描述，到 Code Review，Claude 主导整个流程

#### Q&A

**Q1：MCP Server 会不会有安全风险？Claude 能通过 MCP 删我的数据吗？**

会有风险，但可以控制。MCP Server 能做什么，取决于它暴露的 Tools。只读工具（如 `query_database`）不能删数据，读写工具（如 `execute_sql`）可以。建议：生产数据库只连只读 MCP；Claude 执行 DELETE/DROP 等破坏性操作时，CC 通常会请求确认。

**Q2：`.mcp.json` 应该提交 Git 还是加进 `.gitignore`？**

只有命令和传输配置（无密钥）时，提交 Git，方便团队共享。认证信息用环境变量（`GITHUB_TOKEN` 等）传递，不写进 `.mcp.json`，这样可以安全提交。

**Q3：团队里有人没装某个 MCP，会影响正常开发吗？**

不影响。MCP 是可选增强工具。没有 GitHub MCP，开发者照常写代码、提交、推送，只是无法让 Claude 直接操作 GitHub。CC 只在对应 MCP 已安装时才激活 `.mcp.json` 里的配置。

**Q4：除了 GitHub 和 SQLite，还有哪些常用的 MCP？**

| MCP | 用途 |
|-----|------|
| Filesystem | 读写本地文件 |
| Slack | 发送消息、读取频道 |
| PostgreSQL | 连接 PostgreSQL 数据库 |
| Brave Search | 让 Claude 联网搜索 |
| Sentry | 读取错误报告 |

可在 [modelcontextprotocol.io](https://modelcontextprotocol.io) 查看官方维护的 MCP Server 列表（以实际网站内容为准）。

### 9.1 动手：用 Headless 审查单个文件

#### 动手：最简单的 Headless 调用

先确认你在项目目录下，然后试试下面这条命令：
> **路径说明**：以下脚本中的路径示例以 Next.js App Router 为准。
> - API 路由：`app/api/**/*.ts`（如 `app/api/tasks/route.ts`）
> - 中间件：`app/middleware.ts`
>
> 如果你的项目初始化时 Claude 选择了 Express 方案，对应路径为 `src/routes/*.ts`，请将脚本中的 glob 模式自行替换。


```bash
cat app/api/tasks/route.ts | claude -p "用中文审查这个文件，找出潜在的安全问题，输出格式：问题描述 + 风险等级（高/中/低）+ 修复建议"
```

你会看到**类似**这样的输出（具体内容取决于文件实际代码）：

```
问题 1：缺少输入验证
描述：createTask 接口未验证 title 字段长度，可能导致超长字符串写入数据库
风险等级：中
修复建议：添加 zod schema 验证，限制 title 最大 200 字符

问题 2：缺少认证中间件
描述：DELETE /tasks/:id 路由未验证用户身份，任何人都可以删除任意任务
风险等级：高
修复建议：添加 requireAuth 中间件，验证 JWT token
```

> 这就是 Headless 模式最直接的价值：不需要打开 Claude Code 界面，一条命令出结果。

#### 动手：用 JSON 格式输出，方便程序处理

```bash
cat app/api/tasks/route.ts | claude -p \
  '审查这个文件，输出严格的 JSON，格式：{"issues": [{"desc": "问题描述", "severity": "high|medium|low", "fix": "修复建议"}], "overall": "pass|warn|fail"}' \
  --output-format json \
  --max-turns 3
```

JSON 格式输出的好处：你可以用 `jq` 过滤高风险问题，或者把结果写入日志文件供后续分析。

```bash
# 只看 high 级别问题（需要安装 jq）
cat app/api/tasks/route.ts | claude -p \
  '审查输出 JSON: {"issues": [{"desc": "...", "severity": "high|medium|low"}]}' \
  --output-format json | jq '.issues[] | select(.severity == "high")'
```

### 9.2 Headless 模式是什么

> 问题：怎么让 Claude 在没有人盯着的情况下自动运行？
> 心智模型：命令行调用，脚本驱动

#### 动手：第一个 Headless 命令

在终端运行：

```bash
echo "function add(a, b) { return a + b }" | claude -p "这段代码有什么问题？" --output-format text
```

观察：Claude 直接输出结果后退出，没有打开交互界面。这就是 Headless 模式——适合脚本调用。

#### 理论：从"对话模式"到"命令模式"

你平时用的 `claude`（直接启动，进入交互界面）是**交互模式**。

Headless 模式用的是 `claude -p`，全称是 `--print`。它不打开交互界面，直接执行一个任务，输出结果，然后退出。

```bash
# 交互模式（你平时用的）
claude

# Headless 模式（本章要学的）
claude -p "帮我分析这段代码的安全问题"
```

差别在哪？

| 维度 | 交互模式 | Headless 模式 |
|------|----------|---------------|
| 启动方式 | `claude` | `claude -p "任务"` |
| 需要人守着 | 是 | 否 |
| 适合场景 | 开发、探索、调试 | CI/CD、定时任务、批量处理 |
| 可以被脚本调用 | 否 | 是 |
| 上下文保持 | 是（对话持续） | 每次独立（或用 `-c` 继续） |

#### 理论：核心参数详解

**已确认参数**（Claude Code 2.x 中稳定存在）：

```bash
# 最基础用法：执行一个任务
claude -p "提示词"

# 从文件读取，通过管道传入
cat app/api/tasks/route.ts | claude -p "审查这个文件的安全问题"

# 继续上一次对话（Headless 也支持）
claude -p -c "继续上面的任务"

# 指定输出格式
claude -p "任务" --output-format text          # 纯文本（默认）
claude -p "任务" --output-format json          # JSON 格式，方便程序处理
claude -p "任务" --output-format stream-json   # 流式 JSON，逐行输出

# 限制最大轮次（防止无限循环，CI 环境推荐设置）
claude -p "任务" --max-turns 5

# 指定模型
claude -p "任务" --model claude-opus-4-5

# 跳过权限确认（仅 CI 环境使用，见下方风险说明）
claude -p "任务" --dangerously-skip-permissions
```

**可能存在的参数**（以实际版本为准，不同版本可能有差异）：

```bash
# 限制 API 费用上限（以实际版本为准）
claude -p "任务" --max-budget-usd 0.5

# 自定义系统提示词（以实际版本为准）
claude -p "任务" --system-prompt "你是一个安全审查专家"

# 追加系统提示词，在默认提示词之后补充（以实际版本为准）
claude -p "任务" --append-system-prompt "审查时重点关注 SQL 注入"
```

> **--dangerously-skip-permissions 风险说明**：这个参数会跳过所有权限确认弹窗，让 Claude 直接执行文件操作、运行命令。在 CI/CD 环境中必须加这个参数（因为没有人坐在那里按 Enter），但**永远不要在本地开发时使用**。CI 环境通常是隔离的沙盒，风险可控；本地开发环境中误用可能导致文件被意外修改或删除。

### 9.3 动手：写 Shell 脚本批量审查 task-manager 代码

手动一个个文件审查太慢。写一个脚本，自动扫描所有 API 文件：

#### 动手：创建批量审查脚本

1. 创建脚本目录和文件：

   ```bash
   mkdir -p scripts
   ```

2. 将以下内容保存为 `scripts/security-audit.sh`：

```bash
#!/bin/bash
shopt -s globstar  # 启用递归 glob（**）
# task-manager 批量安全审查脚本
# 用法：bash scripts/security-audit.sh

set -e

echo "=== task-manager 安全审查 ==="
echo "时间：$(date)"
echo ""

FAIL_COUNT=0
WARN_COUNT=0
PASS_COUNT=0

# 遍历所有 TS 路由文件
for file in app/api/**/*.ts; do
  # 跳过不存在的匹配（当目录为空时）
  [ -f "$file" ] || continue

  echo "审查：$file"

  # 调用 Headless Claude，输出 JSON
  result=$(cat "$file" | claude -p \
    '你是安全审查专家。审查这个 TypeScript 文件，输出严格的 JSON（不要加代码块标记），格式：
    {"overall": "pass|warn|fail", "issues": [{"desc": "问题", "severity": "high|medium|low", "fix": "修复"}]}
    没有问题时 issues 为空数组，overall 为 pass。' \
    --output-format text \
    --max-turns 2 \
    --dangerously-skip-permissions 2>/dev/null)

  # 提取 overall 字段（简单解析，不依赖 jq）
  overall=$(echo "$result" | grep -o '"overall": *"[^"]*"' | grep -o '"[^"]*"$' | tr -d '"')

  case "$overall" in
    fail)
      echo "  [FAIL] 发现高风险问题"
      FAIL_COUNT=$((FAIL_COUNT + 1))
      ;;
    warn)
      echo "  [WARN] 发现中低风险问题"
      WARN_COUNT=$((WARN_COUNT + 1))
      ;;
    pass)
      echo "  [PASS] 未发现问题"
      PASS_COUNT=$((PASS_COUNT + 1))
      ;;
    *)
      echo "  [SKIP] 解析结果失败"
      ;;
  esac

  echo ""
done

echo "=== 审查汇总 ==="
echo "通过：$PASS_COUNT 个文件"
echo "警告：$WARN_COUNT 个文件"
echo "失败：$FAIL_COUNT 个文件"

# 如果有高风险问题，脚本以非零退出码退出（CI 会认为 job 失败）
if [ "$FAIL_COUNT" -gt 0 ]; then
  echo ""
  echo "[错误] 存在高风险安全问题，请修复后再提交"
  exit 1
fi

echo ""
echo "审查完成。"
```

3. 赋予执行权限：

   ```bash
   chmod +x scripts/security-audit.sh
   ```

#### 动手：运行批量审查

在 task-manager 根目录执行：

```bash
bash scripts/security-audit.sh
```

> **提示**：脚本本身使用 `grep` 解析 JSON 输出，无需额外安装工具，直接运行即可。
> 若需用 `jq` 手动过滤结果（如 9.2 节示例中的 `| jq '.issues[] | ...'`），
> macOS 用 `brew install jq`，Linux 用 `apt install jq`。

#### 观察：批量审查输出示例

脚本执行完毕，你会看到类似这样的汇总输出：

```text
=== task-manager 安全审查 ===
时间：Mon Feb 24 10:30:00 CST 2026

审查：app/api/tasks/route.ts
  [FAIL] 发现高风险问题

审查：app/api/comments/route.ts
  [WARN] 发现中低风险问题

审查：app/components/TaskList.tsx
  [PASS] 未发现问题

=== 审查汇总 ===
通过：1 个文件
警告：1 个文件
失败：1 个文件

[错误] 存在高风险安全问题，请修复后再提交
```

将这份报告粘贴给 Claude：“请根据以上安全审查报告，按优先级修复所有高危问题”，让 Claude 批量修复。

> **提示**：若需查看每个文件的详细问题列表，可对单个文件单独运行 9.2 节的 Headless 命令：
> `cat app/api/tasks/route.ts | claude -p "检查此文件的安全问题"`

> **关键点**：脚本最后用 `exit 1` 返回失败状态。这是 CI/CD 的约定 — 非零退出码代表失败，CI 系统会自动把这个 job 标红，阻止 PR 合并。

### 9.4 GitHub Actions 集成（US-8：PR 自动审查）

这一节实现 **US-8**：作为技术负责人，我想 PR 提交后自动触发 AI 代码审查，无需人工介入。

#### 理论：GitHub Actions 与 Claude Code

Anthropic 官方发布了 `anthropics/claude-code-action`，这是一个真实存在的 GitHub Actions Action，可以直接在 `.github/workflows/` 中使用。

它的工作原理：
1. PR 创建或更新时，GitHub Actions 触发 workflow
2. `claude-code-action` 启动 Headless Claude，传入 PR 的 diff 内容
3. Claude 审查代码变更，把审查意见作为 PR comment 发布
4. 如果发现严重问题，可以配置为阻止合并

#### 动手：给 task-manager 配置自动 PR 审查

**第 1 步：在 GitHub 仓库中设置 Secret**

1. 打开你的 GitHub 仓库页面
2. 进入 Settings → Secrets and variables → Actions
3. 点击 New repository secret
4. Name 填 `ANTHROPIC_API_KEY`，Value 填你的 API Key
5. 保存

**第 2 步：创建 workflow 文件**

在 task-manager 项目根目录创建 `.github/workflows/claude-review.yml`：

```yaml
name: Claude Code Review

on:
  pull_request:
    types: [opened, synchronize]
    # 只审查以下路径的变更，减少不必要的 API 调用
    paths:
      - 'app/**'
      - '**/*.test.ts'
      - '**/*.spec.ts'
      # 根据你的项目实际目录结构调整

jobs:
  code-review:
    runs-on: ubuntu-latest
    # 需要写入 PR comment 的权限
    permissions:
      contents: read
      pull-requests: write

    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        with:
          # 获取完整 diff 需要 fetch-depth: 0
          fetch-depth: 0

      - name: Claude Code Review
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          # 审查提示词：告诉 Claude 审查什么、输出什么格式
          prompt: |
            你是 task-manager 项目的代码审查专家。
            请审查这个 PR 的代码变更，重点检查：
            1. 安全问题（SQL 注入、未验证的用户输入、缺少认证）
            2. 代码质量（函数长度、变量命名、重复代码）
            3. 测试覆盖（新功能是否有对应测试）
            4. CLAUDE.md 规范遵守情况

            输出格式：
            ## 审查结论：[通过 / 需要改进 / 阻止合并]

            ### 发现的问题
            - [高/中/低] 问题描述 → 修复建议

            ### 亮点
            - 做得好的地方

            如果没有问题，直接输出"审查通过，代码质量良好"。
```

**第 3 步：提交并推送**

```bash
git add .github/workflows/claude-review.yml
git commit -m "ci: 添加 Claude Code 自动 PR 审查"
git push
```

**第 4 步：验证**

创建一个测试 PR（可以是一个小改动），你会在 PR 页面的 Checks 区域看到 `Claude Code Review` 这个 job 正在运行。等它完成，检查 PR 的 Comments 区域，Claude 的审查意见会自动出现。

#### 观察：审查意见长什么样

Claude 大致会生成这样的 comment（实际内容取决于你提交的代码）：

```
**审查结论：需要改进**

**发现的问题**
- [高] app/api/tasks/route.ts 第 42 行：缺少对 taskId 的格式验证，
  传入非数字 ID 会触发数据库错误并暴露内部错误信息
  → 修复建议：添加 `z.string().uuid()` 验证

- [中] src/services/taskService.ts：findAll 方法缺少分页，
  任务量大时可能导致响应超时
  → 修复建议：添加 limit/offset 参数

**亮点**
- 认证中间件封装干净，所有路由都正确引用
- 错误处理统一，没有裸露的 500 错误
```

## Ch10 Agent Teams — 多代理团队协作（实验性，选讲）

> 本章内容：Agent Teams 多代理协作（实验性，选讲）
>
> 注意：本章功能仍处于实验阶段，不纳入作业考核。目标是了解原理、知道能力边界。

> 预计时长：20 分钟
> ⚠️ 本章为实验性功能，以实际 Claude Code 版本为准。以下内容基于公开文档，具体行为可能随版本更新而变化。

---

### 引出

> 问题：Sub Agent 让你把子任务委托给专属 Agent（如 security-reviewer）按需处理。但如果任务很大，需要安全审查、性能审查、测试覆盖审查同时进行呢？你得一个一个等。
> 心智模型：从一个助手到一支团队

---

### 10.1 理论：Agent Teams vs Sub Agent

#### 理论：两种协作模式的本质区别

你在中级课程里已经学了 Sub Agent — 主 Claude 把子任务委托给一个 Agent，等它完成后继续。

Agent Teams 不同：多个 Claude Code 实例组成一个团队，成员之间直接通信，共享一份任务列表，自主认领和协调。

| 维度 | Sub Agent | Agent Teams（实验性） |
|------|-----------|----------------------|
| 实例数量 | 1 主 + N 子 | N 个平等成员（有 Lead） |
| 通信方式 | 子汇报给主 | 成员之间直接通信 |
| 任务认领 | 主动分配 | 成员自主认领 |
| Token 消耗 | 低 | 高（多实例并行） |
| 适合场景 | 顺序子任务 | 可并行的大型任务 |
| 稳定性 | 稳定 | 实验性，可能有 Bug |

#### 理论：什么时候值得用 Agent Teams

不是所有任务都需要团队。以下场景比较合适（实验性，以实际效果为准）：

**适合**：
- 对同一个 PR 同时做安全审查 + 性能审查 + 测试覆盖审查（互相独立，可并行）
- 竞争性调试：多个 Agent 同时测试不同的 Bug 假设，看谁先找到答案
- 前端 + 后端 + 测试的并行开发（文件不重叠）

**不适合**：
- 多个 Agent 需要修改同一个文件（容易产生冲突）
- 有严格依赖顺序的任务（A 完成才能开始 B）
- 任务总量小（Sub Agent 已经够用，团队模式 Token 消耗不划算）

**动手**：
1. 回想你用 Ch3 Sub Agent 处理过的一个任务（或想象一个实际工作场景）。
2. 对照上方"适合 / 不适合"列表，判断它更适合 Sub Agent 还是 Agent Teams，写下你的理由（一句话即可）。
3. 对照对比表的"Token 消耗"行，说出为什么小任务不值得使用 Agent Teams。

**观察**：大多数日常任务仍属于顺序子任务，Sub Agent 已经够用。Agent Teams 真正发挥价值的场景是"多个维度可以完全独立并行"的大型审查或开发任务。

---

### 10.2 启用方式（实验性）

#### 理论：如何开启 Agent Teams

Agent Teams 是实验性功能，需要手动启用。在 `~/.claude/settings.json`（全局设置）或项目的 `.claude/settings.json`（项目级设置）中添加：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "true"
  }
}
```

> ⚠️ 这个配置键名以"EXPERIMENTAL"开头，说明 Anthropic 官方认为它还不稳定。生产项目中谨慎使用。

启用后，Claude Code 会在合适的时候（任务规模足够大）自动提议组建团队，或者你可以在提示词中明确请求。

**动手**：
1. 打开 `~/.claude/settings.json`（若不存在则新建）。
2. 在 `"env"` 字段中查找是否已有 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`；如果没有，将上方代码块的内容添加进去。
3. 保存文件，确认 JSON 格式正确（无多余逗号或括号缺失）。
4. 重新启动 Claude Code，在 task-manager 目录下输入一个大型任务提示词，观察 CC 是否在响应中出现"多 Agent"或"组建团队"的提示：
   ```
   请用多个 Agent 并行审查 task-manager 项目：安全审查、性能审查、测试覆盖各一个
   ```

**观察**：如果 CC 响应中出现了"正在组建 Agent 团队"或类似提示，说明实验性功能已生效。如果 CC 正常响应但没有多 Agent 提示，说明当前版本不支持此功能，或任务规模未达到触发阈值——此时改用本节"分屏模式"的手动方案完成串联练习。键名中的 `EXPERIMENTAL` 是 Anthropic 给出的明确信号：遇到异常行为属正常，不要在生产项目中依赖此功能。

---

### 10.3 基本用法与适用场景

#### 理论：第一步 — 如何启动 Agent Teams（实验性，以实际版本为准）

启用实验性开关后（见 10.2），启动 Agent Teams 的方式是**在 Claude Code 中用自然语言描述任务和团队结构**，Claude 会自动创建团队并分配角色，不需要额外命令。

例如，直接输入：

```
请用三个 Agent 并行审查这个项目：
- Agent 1：负责安全审查，检查所有路由和权限
- Agent 2：负责性能审查，分析数据库查询
- Agent 3：负责测试覆盖率，检查 tests/ 目录
最后汇总三份报告
```

Claude 收到指令后会自动组建团队，每个成员认领自己的子任务，开始并行执行。

> 注意：以上为操作流程描述，具体触发方式以实际版本的界面为准。

#### 理论：两种运行模式

**模式一：In-process 模式（同一终端窗口）**

Claude Code 在内部启动多个 Agent 实例。启动后，主 Claude 会在对话中实时汇报各队友的认领情况和进度更新；你也可以通过 `Shift+Down` 键切换查看某个队友的当前工作内容（实验性，以实际版本为准）。

优点：不需要额外开窗口，操作简单。
缺点：你只能"看"，不能同时看到所有队友的实时输出。

**模式二：分屏模式（tmux 或 iTerm2）**

更稳定的替代方案。你手动开几个终端窗口，每个窗口跑一个 Claude Code 实例，通过共享的 Todo 文件协调任务。

```bash
# 窗口 1：安全审查 Agent
claude
# 在里面说：你是安全审查专家，审查 task-manager 的所有路由文件，把结果写入 review-security.md

# 窗口 2：性能审查 Agent
claude
# 在里面说：你是性能专家，审查 task-manager 的数据库查询，把结果写入 review-perf.md

# 窗口 3：测试覆盖 Agent
claude
# 在里面说：你是测试专家，检查 task-manager 的测试覆盖率，把结果写入 review-tests.md
```

> 分屏模式虽然需要手动操作，但比 Agent Teams 实验性功能更稳定，在实际项目中更推荐。

#### 理论：共享任务列表机制

Agent Teams 协调的核心是一份共享的任务列表（实验性，以实际版本为准）：

```
任务状态流转：
pending → in progress → completed

例：
[ pending    ] 审查 auth.ts 的安全问题
[ in progress] 审查 tasks.ts 的性能问题  ← Agent B 正在做
[ completed  ] 检查测试覆盖率             ← Agent C 已完成
```

成员自主认领 `pending` 状态的任务，完成后标记为 `completed`，Lead 可以分配任务或审批方案。这套机制让多个 Agent 不会重复干同一件事。

在 in-process 模式下，主 Claude 会在对话中实时汇报各队友的认领情况和进度更新；切换到某个队友（`Shift+Down`）后，可以直接看到它当前正在处理的内容。

**动手**：
1. 针对 task-manager 项目，在纸上或编辑器里写出一个 3-Agent 分工方案：每个 Agent 负责哪个目录或哪个审查维度，输出写到哪个文件。
2. 检查你的方案：三个 Agent 的文件职责是否有重叠？如果有，调整分工直到完全不重叠。
3. 参考上方分屏模式的代码块，把你的方案改写成 3 条 `claude` 启动注释（不需要真正执行）。

**观察**：在动手写分工方案时，你会发现"文件不重叠"比听起来更难——尤其是共享 utils 或 config 文件。这正是使用 Agent Teams 前必须提前规划的核心工作。

---

### 10.4 注意事项

#### 理论：使用 Agent Teams 前必须了解的限制

**Token 消耗（最重要）**

每个 Agent 实例都有独立的上下文，多实例并行意味着 Token 消耗成倍增加。一个 4 Agent 团队的 Token 消耗可能是单 Agent 的 3-5 倍（取决于共享信息量）。

建议：用 Agent Teams 前，先估算任务是否值得这个成本。小任务用 Sub Agent，大型并行任务才考虑 Agent Teams。

**文件冲突**

如果两个 Agent 同时修改同一个文件，会产生冲突，甚至互相覆盖对方的修改。使用 Agent Teams 时，要明确划分每个 Agent 的文件职责范围，确保不重叠。

**动手**：
1. 打开 task-manager 项目的文件列表（`ls app/` 或在编辑器里浏览）。
2. 假设你要派两个 Agent 同时修改这个项目，找出至少一个"两个 Agent 都可能动到的文件"（如共享的 `utils.ts` 或 `types.ts`）。
3. 写下你会如何处理这个潜在冲突：是让某个 Agent 专门负责这个文件，还是在动手前先把它拆分？

**观察**：共享文件（types、utils、constants）是 Agent Teams 中最容易产生冲突的地方，提前识别比事后处理冲突成本低得多。

**不支持会话恢复**

Agent Teams 会话意外中断后，无法像单 Agent 一样用 `/resume` 或 `-c` 继续。中断意味着需要重新开始。重要任务建议先让 Agent 把中间结果写入文件，降低中断损失。

**建议的最佳实践**：

```
1. 先把大任务拆成互相独立的子任务（文件不重叠）
2. 每个 Agent 负责一类文件或一个维度
3. 指定一个 Lead Agent 最后做汇总
4. 把每个 Agent 的结果写入独立的输出文件
5. 遇到问题先降级到分屏 + 手动协调模式
```

#### 动手：体验双 Agent 分工审查

用两个 Claude Code 实例同时审查 task-manager 的不同模块，最后汇总结果：

**第 1 步：打开两个终端窗口**

两个窗口都进入 task-manager 目录，分别启动 Claude Code。

**第 2 步：分工审查**

- 终端 1（安全审查）输入：
  > 审查 app/api/ 目录下所有 API 路由的安全性（输入验证、错误处理、权限检查），列出发现的问题

- 终端 2（性能审查）输入：
  > 审查 app/ 目录下所有组件的性能（不必要的重渲染、大列表优化、接口调用频率），列出发现的问题

**第 3 步：在第三个终端汇总**

两个审查都完成后，在新终端启动 Claude Code，输入：
> 安全审查发现了 [粘贴终端 1 的结果]，性能审查发现了 [粘贴终端 2 的结果]。
> 按优先级排序，给出修复顺序建议。

#### 观察

即使没有 Agent Orchestration API，手动协调两个 Claude 实例也能体验「并行审查 + 中心汇总」的多 Agent 工作流。这就是 Ch10 介绍的核心思路——未来随着 CC 的 Agent Teams 功能成熟，这个协调过程会自动化。

#### 小结

| 知识点 | 关键点 |
|--------|--------|
| Agent Teams vs Sub Agent | 团队成员平等通信 vs 子汇报给主 |
| 启用方式 | settings.json 中设置 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "true"` |
| In-process 模式 | `Shift+Down` 切换队友（实验性） |
| 分屏模式 | tmux/iTerm2 多窗口，更稳定 |
| 共享任务列表 | pending → in progress → completed（实验性） |
| 核心限制 | Token 消耗高、文件冲突风险、不支持恢复 |

### Q&A

1. 我用 Sub Agent 已经可以并行了（主 Agent 同时发起多个子任务），和 Agent Teams 有什么本质区别？什么时候才需要 Agent Teams？

2. Agent Teams 标注"实验性"，在实际项目里要不要用？你会怎么决策？

3. 分屏模式（tmux + 多个 claude 实例）和 Agent Teams 的 in-process 模式，各有什么优缺点？

### 11.3 作业说明

#### 作业：强化并扩展你的 task-manager 工具链

今晚的作业在已有的 task-manager 基础上继续扩展，把中级课程的所有工具整合到一起。

**必做部分**：

```
1. 给 task-manager 再创建 1 个新 Skill（自选功能）
   要求：
   - 在 .claude/skills/ 目录下创建，文件名体现功能
   - Skill 有明确的步骤和验证标准
   - 在课上演示时要能用这个 Skill 完成实际任务
   示例方向（任选其一或自定）：
   - add-api-endpoint：标准化新增接口的流程
   - refactor-service：提取 service 层的标准步骤
   - write-e2e-test：E2E 测试的标准流程

2. 给 security-reviewer Agent 增加针对 task-manager 的特定检查项
   要求：
   - 在 Agent 的 system prompt 中加入项目特定规则
   - 至少 3 条具体规则（比如"检查 taskId 是否做了 UUID 验证"）
   - 说明为什么这些规则对 task-manager 特别重要

3. 配置完整的 Hook 工具链
   要求：三个 Hook 都要有：
   - PreToolUse：拦截至少 1 种危险操作（自定义，比如防止直接修改 .env）
   - PostToolUse：编辑 TS 文件后自动格式化（Prettier）
   - Stop：会话结束时自动运行测试，输出覆盖率

4. 打包成 Plugin
   要求：
   - 包含上面所有内容（Skill + Agent + Hook）
   - 写 README.md（放在 Plugin 目录里）说明安装方法和使用方式
   - 确保另一个人拿到这个目录能一键安装

5. 在 GitHub 上创建真实的 PR
   要求：
   - 提交你今天写的代码（新 Skill、Agent 改进、Hook）
   - 用 security-reviewer Agent 审查这个 PR 的变更
   - 把审查结果截图附在 PR Description 里
```

**选做部分**（有兴趣就做，没时间可以跳过）：

```
6. 配置 GitHub Actions 自动审查
   - 按照 9.4 节的步骤，给 task-manager 配置 .github/workflows/claude-review.yml
   - 创建一个测试 PR，验证 Claude 的审查 comment 自动出现

7. 写 Headless 脚本批量检查项目中所有 API 文件
   - 扩展 9.3 节的 security-audit.sh
   - 输出 HTML 或 Markdown 格式的审查报告
   - 报告里要有每个文件的状态和具体问题

8. 用 BMAD-Method 规划一个新功能
   - 选一个你想加入 task-manager 的功能（比如：任务提醒、标签系统、甘特图）
   - 用 BMAD Quick Flow 生成完整的 User Story + Tasks
   - 不需要实现，规划文档有就行

9. 体验 Agent Teams 并发协作（实验性）
   - 开启 Agent Teams 实验性功能
   - 用 3 个 Agent 并行审查 task-manager（安全 + 性能 + 测试各一个）
```

### 11.4 进阶方向（高级课程）

中级课程解决了"怎么用工具"的问题。如果你想继续深入，高级课程解决的是更难的问题：**面对复杂的真实项目，怎么用 Claude Code 做高质量的工程决策？**

高级课程涵盖：

| 主题 | 你会解决什么问题 |
|------|----------------|
| 遗留代码维护 | 接手一个没有文档、没有测试的老项目，怎么快速理解和修改 |
| 大规模重构 | 把一个"意大利面代码库"重构成清晰的分层架构，Claude 如何辅助 |
| TDD 工作流进阶 | 比中级课程更严格的红绿重构循环，复杂业务逻辑的测试策略 |
| AI 友好架构 | 如何设计代码结构，让 Claude 理解得更准、改得更稳 |
| 安全审查进阶 | OWASP Top 10 的提示词模板，系统性地检查常见漏洞 |

高级课程会在你今天搭建的 task-manager 上继续构建，添加更复杂的功能，用更高级的工程实践保障质量。感兴趣可以单独报名。
