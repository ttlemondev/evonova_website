2.2

配置 API 认证

本培训使用统一的 API 代理服务，不需要注册 Anthropic 账号。

详细图文教程：https://academy.claude-code.club/getting-started/quick-start

需要设置 3 个环境变量：

变量值作用
ANTHROPIC_BASE_URLhttps://claude-code.club/apiAPI 代理地址
ANTHROPIC_AUTH_TOKEN课堂提供你的 API 密钥
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC1禁用遥测流量

Linux / WSL（bash）：

bash 
echo 'export ANTHROPIC_BASE_URL="https://claude-code.club/api"' >> ~/.bashrc
echo 'export ANTHROPIC_AUTH_TOKEN="你的API密钥"' >> ~/.bashrc
echo 'export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1' >> ~/.bashrc
source ~/.bashrc

Windows PowerShell：

powershell 
[System.Environment]::SetEnvironmentVariable("ANTHROPIC_BASE_URL", "https://claude-code.club/api", "User")
[System.Environment]::SetEnvironmentVariable("ANTHROPIC_AUTH_TOKEN", "你的API密钥", "User")
[System.Environment]::SetEnvironmentVariable("CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC", "1", "User")

Windows 设置环境变量后需关闭并重新打开终端才能生效。

Claude Code 2.1.90 新增了一个很适合新手的命令：/powerup。

注意命令名是单数：/powerup，不是 /power-ups。

为什么这个命令重要？

  • 很多人刚开始只会 claude、/model、/clear 这些基础操作，很多更强的能力根本没用起来
  • 以前想学高级功能，通常要离开终端去翻文档，上下文一断，就很容易忘
  • 现在学习路径和使用路径合并了：边学边试，学完立刻在当前项目里用

怎么用？

在 Claude Code 提示符下输入：

4.1

没有规则的 Claude

到目前为止，Claude Code 帮你生成了菜单浏览页面，表现不错。但我们来测试一下：当你提一个新需求，Claude 能做到多"懂你"？

输入：

text 
> 我想给菜品加一个"辣度"字段，应该怎么设计？

观察 Claude 的回答 — 它可能给出以下任何一种方案：

  • spicy: boolean（只区分辣/不辣）
  • spicyLevel: 1-5（五级辣度）
  • heat: "mild" | "medium" | "hot" | "extra-hot"（英文枚举）
  • spicy_level: number（不确定范围）

每次问可能得到不同的答案。但我们团队的约定是：辣度用 0-3 整数表示，0=不辣 1=微辣 2=中辣 3=特辣。

Claude 不可能猜到这个约定，因为这是我们自己定义的业务规则，不是行业标准。"辣度怎么表示"有无数种合理方案，哪种都说得通 — 但团队需要的是统一，不是"都说得通"。

这就是问题所在：没有明确的规则文件，Claude 每次都在"自由发挥"。它可能做得不错，但不稳定、不统一。今天写的代码用 1-5，明天写的用 0-3，后天又变成字符串 — 项目越大越混乱。

动手：验证问题解决

4.3

CLAUDE.md 写什么、不写什么

通过刚才的体验你能感受到：CLAUDE.md 里写的规则直接影响 Claude 的输出质量。

核心原则：写 Claude 猜不到的，不写 Claude 本来就知道的。

该写的四类信息

1. 技术栈和架构 — Claude 能从 package.json 猜到依赖，但猜不到你用的是 Express 还是 Koa，数据库用的是 SQLite 还是 PostgreSQL。

2. 常用命令 — 写进去后 Claude 跑命令时不需要每次翻 package.json。

3. 业务规则和约定 — 这是最重要的部分。Claude 最猜不到的就是你的业务逻辑（"价格用分"、"状态不能回退"）。

4. 项目特殊注意事项 — 比如"不要手动修改 migrations 文件"、"前端状态管理用 React Context 不用 Redux"。

不该写的

不该写原因
通用 TypeScript 语法（如 const vs let）Claude 本来就知道
框架的标准用法（如路由规则、组件生命周期）Claude 训练数据里有
长篇教程或设计文档太长浪费 Token，放到单独文档里用 @ 引用
API 密钥、密码、Token安全风险！ 永远不要写在代码仓库里
"请用中文回复" 之类的偏好放到全局 ~/.claude/CLAUDE.md 里，不要污染团队配置

CLAUDE.md 的理想长度

text 
太短（< 10 行） → Claude 缺少关键信息，输出不稳定
刚好（30-100 行）→ 覆盖技术栈 + 命令 + 业务规则 + 约定
太长（> 200 行） → 浪费 Token，每次对话都要加载，拆分到 rules/ 目录

一个写得好的 CLAUDE.md 长什么样？以下是 waimai-app 的理想范本：

markdown 
# 外卖点餐系统 (waimai-app)

## 技术栈
（Ch2 初始化时 CC 选择的全栈方案，如 Next.js + React + SQLite + Tailwind CSS）

## 常用命令
- `npm run dev` — 启动开发服务器
- `npm run test` — 运行单元测试
- `npm run test:e2e` — 运行 E2E 测试

## 业务规则
- 辣度用 0-3 整数表示：0=不辣 1=微辣 2=中辣 3=特辣
- 价格单位统一用"分"（整数），不用"元"（浮点）。2800 = ¥28.00
- 订单状态只能单向流转：pending → preparing → delivering → completed
- 订单状态不能跳步、不能回退
- 菜品分类固定 5 种：川菜、粤菜、湘菜、饮料、甜品

## 代码约定
- API 返回统一格式：{ success, data, error }
- 组件文件用 PascalCase（MenuList.tsx），工具函数用 camelCase（formatPrice.ts）
- 每个 API 路由必须有输入验证

不到 30 行，但涵盖了技术栈 + 命令 + 业务规则 + 代码约定。

配置体系

Claude 的五层配置体系

刚才我们创建的 CLAUDE.md 是团队共享的 — 提交到 Git，所有人 pull 下来都能看到。

但如果小明想用中文注释、小红想用英文注释呢？ 这种个人偏好不应该写进团队共享的 CLAUDE.md。所以 Claude Code 设计了一套多层配置系统，不同层面的需求放不同的地方。

场景

waimai-app 项目，3 个开发者 — 小明（前端）、小红（后端）、小张（Tech Lead）。

五层配置总览

text

├── CLAUDE.md                            ← 第一层：团队共享
├── CLAUDE.local.md                      ← 第四层：个人私有（.gitignore 里）
├── .claude/
│   └── rules/
│       ├── api-conventions.md           ← 第二层：团队共享（拆分）
│       └── testing.md                   ← 第二层：团队共享（拆分）
├── package.json
└── ...（项目源码目录，取决于 CC 选择的技术栈）

~/.claude/                               ← Home 目录（每个人自己的电脑上）
├── CLAUDE.md                            ← 第三层：个人全局偏好
└── projects/
    └── <项目路径编码>/
        └── memory/
            └── MEMORY.md                ← 第五层：Claude 自动记忆

第一层：项目级 `./CLAUDE.md` — 团队共识

就是你刚才创建的那个文件。放在项目根目录，提交到 Git。小明、小红、小张 clone 项目后都能看到。这是最重要的一层，大多数项目只需要这一个文件就够了。

写什么？ 团队所有人都要遵守的核心规则 — 技术栈、常用命令、业务规则、代码约定。

CLAUDE.md 的加载时机：Claude Code 启动时自动读取，不需要你手动 @引用。每一轮对话 Claude 都能看到 CLAUDE.md 的内容。

第二层：项目规则 `.claude/rules/*.md` — 详细规范

和第一层一样是团队共享、提交到 Git 的。区别是按主题拆成多个文件。

text 
CLAUDE.md        → 入职手册第一页（公司简介、核心价值观）
rules/*.md       → 各部门详细操作手册（财务报销流程、代码审查标准...）

CLAUDE.md 写一行"API 返回统一格式：{ success, data, error }"，rules/ 里展开写完整规范。

.claude/rules/api-conventions.md 示例：

markdown 
# API 约定

## 返回格式
所有 API 返回统一格式：
- 成功：{ success: true, data: T }
- 失败：{ success: false, error: "错误描述" }
- 分页：{ success: true, data: T[], meta: { total, page, limit } }

## 状态码
- 200：查询/更新成功
- 201：创建成功
- 400：请求参数错误（附具体字段错误信息）
- 404：资源不存在
- 500：服务器内部错误（不暴露内部细节）

## 输入验证
- 每个 POST/PUT 接口必须有 Zod schema
- 验证失败返回 400 + 具体字段错误

.claude/rules/testing.md 示例：

markdown 
# 测试规范

## 覆盖率要求
- 单元测试覆盖率 ≥ 80%
- 每个 API 路由至少 3 个测试用例（正常、参数错误、资源不存在）

## 命名规范
- 测试文件：与源文件同名 + .test.ts（如 formatPrice.test.ts）
- describe 用函数/模块名，it 用自然语言描述行为

## Mock 规范
- 数据库操作统一 mock
- 不要 mock 内部工具函数，只 mock 外部依赖

Claude 启动时 CLAUDE.md 和 rules/ 全部加载，不需要手动 @引用。

什么时候需要拆？ 规则少于 50 行，直接写在 CLAUDE.md 里。超过 50 行，按主题拆到 .claude/rules/。对于 waimai-app 这个规模的全栈项目，一个 CLAUDE.md 就够了。rules/ 更适合大型团队项目。

第三层：全局个人 `~/.claude/CLAUDE.md` — 你的个人偏好

放在你的 home 目录下，对你电脑上所有项目生效。不同开发者的内容不一样：

小明（前端）的 ~/.claude/CLAUDE.md：

markdown 
- 代码注释用中文
- commit message 用英文，格式：feat: xxx / fix: xxx
- 优先使用函数式编程风格，避免 class
- 不要在代码里留 console.log

小红（后端）的 ~/.claude/CLAUDE.md：

markdown 
- 代码注释用英文
- 每个函数加 JSDoc 注释，包含 @param 和 @returns
- 错误处理用 try-catch，不要用 .catch()
- SQL 相关操作必须有事务保护

小张（Tech Lead）的 ~/.claude/CLAUDE.md：

markdown 
- 回复尽量简洁，不要解释显而易见的内容
- 优先建议重构而非新增代码
- 发现安全问题时立即提醒我

小明的中文注释偏好只影响小明自己。小红在同一个 waimai-app 项目上工作，她的 Claude 会写英文注释。互不干扰。

写什么？ 跟具体项目无关、你在所有项目上都想要的个人偏好 — 语言、注释风格、编程范式。

全局个人规则也支持 ~/.claude/rules/ 拆分，用法和项目级一样。

第四层：项目本地 `./CLAUDE.local.md` — 仅你自己，不共享

放在项目根目录，但自动加入 .gitignore，不会提交。什么时候需要？当你在某个项目里有和团队不一样的本地环境或习惯时。

小明的 waimai-app/CLAUDE.local.md：

markdown 
## 我的本地环境
- 本地数据库路径：C:/Users/xiaoming/data/waimai-dev.db
- 开发服务器端口改成了 3001（因为 3000 被其他项目占了）
- 启动命令：PORT=3001 npm run dev

## 我当前负责的模块
- 正在开发"购物车"功能
- 修改购物车相关代码时，帮我同步更新对应的测试文件

小红的 waimai-app/CLAUDE.local.md：

markdown 
## 我的本地环境
- 本地数据库连接配置在 .env.local 里
- 用 DBeaver 管理数据库

## 调试习惯
- 调试 API 时，帮我生成 curl 命令而不是用 Postman
- 遇到数据库问题时，先打印实际执行的 SQL 语句

写什么？ 个人本地环境差异（端口、路径、工具）、当前负责的模块、个人调试习惯。这些写到团队共享的 CLAUDE.md 里会干扰其他人。

第五层：自动记忆 — Claude 自己维护

位置：~/.claude/projects/<项目路径编码>/memory/MEMORY.md

路径中的 <项目路径编码> 是 Git 仓库根目录的完整路径，分隔符替换为 --。比如项目在 E:\projects\waimai-app，对应的记忆目录就是 ~/.claude/projects/E--projects--waimai-app/memory/。你不需要记这个路径，用 /memory 命令就能直接查看和编辑。

你不需要手动写这个文件。Claude 在和你多次协作后，会自动记下它观察到的模式：

markdown 
# Memory

## 项目结构
- 前端页面和组件在对应的页面目录下
- API 路由在项目的 API 目录下
- 数据库配置和模型定义在独立文件中

## 用户偏好
- 用户习惯先写测试再写实现
- 用户喜欢用 const 箭头函数而不是 function 声明
- 修改 API 后，用户通常会要求同步更新前端调用代码

## 常见问题
- 修改数据库表结构后，可能需要重新初始化数据库
- 前端修改后如果页面没更新，尝试清除浏览器缓存或硬刷新

自动记忆是 Claude 跨会话积累的"经验"。关闭 Claude 再打开，它还记得上次学到的东西。你也可以用 /memory 手动查看和编辑这些记忆文件。

团队协作：这些文件怎么共享？

答案：没有任何特殊机制，就是靠 Git。

CLAUDE.md 和 .claude/rules/*.md 就是普通的文本文件，和你项目里的 package.json、tsconfig.json 没有区别。Claude Code 看的是本地文件系统，不是远程仓库。它不知道也不关心你用的是 GitHub、GitLab、Gitee 还是公司自建的 Git 服务器。只要项目目录里有这些文件，Claude Code 启动时就会自动读取。

text 
小张写好 CLAUDE.md → git add → git commit → git push
小明 git pull       → 本地自动出现 CLAUDE.md → 启动 claude → 自动读取
小红 git pull       → 同样拿到 CLAUDE.md → 她的 Claude 也按规则行事
文件提交到 Git？团队成员能看到？
./CLAUDE.md是能 — pull 下来就有
.claude/rules/*.md是能 — pull 下来就有
./CLAUDE.local.md否，自动加入 .gitignore不能 — 只在你本地
~/.claude/CLAUDE.md否，在 home 目录不能 — 只在你电脑上
~/.claude/projects/*/memory/否，在 home 目录不能 — 只在你电脑上

CLAUDE.local.md 创建时，Claude Code 会自动往 .gitignore 追加一行，所以 git add . 也不会意外提交上去。

典型的团队协作流程：

text 
1. Tech Lead 创建 CLAUDE.md + .claude/rules/，push 到仓库
2. 团队成员 clone/pull，自动获得团队规则
3. 每个人各自创建 ~/.claude/CLAUDE.md（个人偏好）和 CLAUDE.local.md（本地环境差异）
4. 团队规则有更新 → Tech Lead 修改后 push → 成员 pull 即可

和项目里其他配置文件（ESLint、Prettier、tsconfig）的协作方式完全一致。没有新概念，没有额外工具。

五种常用权限模式

权限模式

五种常用权限模式

Plan 只读分析，适合先理解陌生项目。

还记得 Ch2 和 Ch3 里的权限确认吗？每次 Claude 要跑命令都弹确认，按 Enter 按到手酸。其实可以调整 Claude 的自主程度。

2026 年 3 月，Claude Code 新增了 Auto Mode。它介于 Accept Edits 和 Bypass 之间：比前两者更少打断，但又不像 Bypass 那样完全跳过安全检查。

动手：体验模式切换

先别看理论，直接动手感受：

第 1 步：按 Shift+Tab，注意终端底部出现 ⏵⏵ accept edits on — 你现在进入了 Accept Edits 模式。

第 2 步：输入以下命令：

text 
> 帮我创建一个工具函数 formatPrice，把分转换成元的显示格式（如 2800 → "¥28.00"）

注意：文件创建不再弹确认了，Claude 直接执行。

第 3 步：按 Shift+Tab 两次，回到 Normal 模式（底部提示消失）。输入：

text 
> 帮我创建一个工具函数 formatDate，格式化日期显示

注意：这次弹确认了，需要按 Enter 允许。

第 4 步（可选，账号支持时）：退出当前会话，重新启动：

bash 
claude --enable-auto-mode

然后按 Shift+Tab 切到 Auto 模式，输入：

text 
> 帮我给购物车加一个 subtotal 字段，并顺手跑一下相关测试

注意：如果你的账号和模型支持 Auto Mode，Claude 会明显减少权限弹窗；但被后台安全分类器判定为高风险、越权或访问不受信基础设施的动作，仍可能被拦下或退回人工确认。

你感受到区别了吗？ Normal 模式每一步都要确认，Accept Edits 模式文件修改自动执行，Auto 模式则是新增的"更少打断，但不完全裸奔"的中间路线。下面来看完整的模式体系。

五种常用模式总览

模式Claude 能自动做什么需要你确认什么适用场景
Plan读取文件、分析代码所有修改和命令探索陌生项目，只看不改
Normal（默认）读取文件编辑文件、运行命令日常使用，一步步确认
Accept Edits读取文件、编辑文件运行命令信任 Claude 的代码修改，只审批命令
Auto（新增）读取文件、编辑文件、运行大部分命令高风险动作，或 classifier fallback 后的动作长任务、批量修改、边改边测
Bypass一切操作无需确认完全信任、隔离环境、自动驾驶

说明：官方完整权限体系里还有 dontAsk 模式（只允许白名单工具，适合 CI 和严格受控环境）。初级课程先掌握最常用的这 5 种。

text 
安全程度：Plan > Normal > Accept Edits > Auto > Bypass

Plan         = 只读模式，Claude 只能看不能改
Normal       = 默认模式，改文件和跑命令都要你确认
Accept Edits = 半自动，文件修改自动执行，命令还要确认
Auto         = 更少打断，动作先过后台安全分类器
Bypass       = 全自动，所有操作无需确认，且没有安全检查（谨慎使用！）

如何切换模式

方式一：会话中按 Shift+Tab

默认情况下，Shift+Tab 会在 Normal、Accept Edits、Plan 三个模式之间循环切换。

如果你在启动时加了 --enable-auto-mode，循环会扩展为：

text 
Normal → Accept Edits → Plan → Auto

终端底部会显示当前模式，常见提示如下：

text 
Normal 模式       → 底部无特殊提示（默认状态）
Accept Edits 模式 → 底部显示 "⏵⏵ accept edits on"
Plan 模式         → 底部显示 "⏸ plan mode on"

注意：Auto 只有在启动时加了 --enable-auto-mode 才会出现在 Shift+Tab 循环里；Bypass 默认也不建议放进循环，初学者一般通过命令行参数按需启动即可。

方式二：启动时指定模式

bash 
claude --permission-mode plan          # 以 Plan 模式启动
claude --permission-mode acceptEdits   # 以 Accept Edits 模式启动
claude --enable-auto-mode              # 解锁 Auto 模式，供 Shift+Tab 切换
claude --enable-auto-mode --permission-mode auto  # 满足条件时直接以 Auto 模式启动
claude --dangerously-skip-permissions  # 以 Bypass 模式启动（等价于 bypassPermissions）

每个模式详解

Normal（默认）— 新手推荐

刚才你已经体验过了：Claude 每次要修改文件或运行命令时，都会暂停让你确认。

优点：你能看到每一步操作，完全掌控。
缺点：频繁确认，按 Enter 按到手酸。

Accept Edits — 日常开发推荐

刚才你也体验了：文件修改自动执行，只有终端命令（如 npm run test）还需确认。

这是熟练用户最常用的模式。文件修改可以用 git diff 事后审查，但命令执行不可逆（比如删除文件），所以命令仍需确认。

Plan — 探索模式

Claude 只能读取和分析，不能做任何修改。适合：

  • 刚拿到一个陌生项目，先了解再动手
  • 让 Claude 出方案但不执行，你审查方案后再决定
  • 代码审查场景，只分析不改动
text 
你：分析一下这个项目的数据库设计有什么问题
Claude：（读取数据库配置文件，分析后给出建议）
       1. 菜品表结构合理，字段覆盖了基本需求
       2. 建议：缺少订单相关的表，后续需要新增
       3. 建议：可以加索引优化按分类查询的性能...

       ⏸ Plan 模式 — 以上只是分析，不会做任何修改

Auto — 新增的中间路线

Auto 模式会让 Claude 自动执行编辑和命令，不再像 Normal / Accept Edits 那样频繁弹确认；但每个动作在执行前，都会先经过后台 classifier（安全分类器）检查。

它主要拦三类事：

  • 超出你任务范围的动作
  • 访问不受信的外部基础设施
  • 可能被恶意文件或网页内容诱导的操作（prompt injection）

适用场景：

  • 长时间重构、批量改文件、边改边跑测试
  • 你信任 Claude 的总体方向，但又不想直接开 Bypass
  • 团队希望减少打断频率，同时保留一层安全网

限制和注意事项：

  • 需要 claude --enable-auto-mode
  • 截至 2026 年 3 月，Team 可用，Enterprise / API 正在 rollout；团队环境里通常还需要管理员先开启
  • 需要 Sonnet 4.6 或 Opus 4.6；不支持 Haiku、Claude 3，以及 Bedrock / Vertex / Foundry 等第三方 provider
  • 如果 classifier 连续拦 3 次，或单会话累计拦 20 次，会退回人工确认

Auto Mode 是 research preview。它比 Bypass 安全，但不等于绝对安全；敏感操作仍然建议人工审查。

Bypass — 全自动（谨慎！）

Claude 的所有操作都自动执行，不弹任何确认。--dangerously-skip-permissions 本质上就是 --permission-mode bypassPermissions。参数名字故意起得很长、很吓人，就是为了提醒你：这个操作有风险，请确认你知道自己在做什么。

适用场景：

  • Docker 容器或虚拟机等隔离环境（搞坏了不心疼）
  • CI/CD 自动化流水线（无人值守，没人按确认）
  • 一次性的临时环境

生产项目中不建议使用 Bypass — 一个错误的 rm -rf 就够你哭的。如果要用，建议先 git commit 保存当前状态，出了问题可以回滚。团队管理员可以通过配置 permissions.disableBypassPermissionsMode 禁止团队成员使用此模式。

维度Auto ModeBypass（--dangerously-skip-permissions）
启用方式claude --enable-auto-mode 后再切换，或直接 --permission-mode autoclaude --dangerously-skip-permissions

Prompt Injection 防护有一定防护，但不保证绝对安全没有

加入一个新团队，面对一个完全陌生的代码仓库？Claude Code 可以帮你快速搞清楚项目全貌。

text

5.1

上下文窗口 — Claude 的"内存"

上下文

上下文窗口与压缩策略

动手：看看你的"内存"用了多少

从 Ch2 到现在，你已经和 Claude 聊了不少 — 初始化全栈项目、构建菜单浏览页面、配置购物车功能、写 CLAUDE.md。Claude 还记得这些吗？

输入：

text 
> /context

你会看到一个彩色网格图，显示当前的"内存"使用情况：

  • 哪些空间被 CLAUDE.md 占了
  • 哪些被对话历史占了
  • 还剩多少可用

这就是 Claude 的"内存"

程序员都知道 RAM：你的电脑有 16GB 内存，开太多应用就会卡。

Claude 的上下文就是它的 RAM — 装得下的它就记得，装不下的就忘了。

text 
你的电脑：16GB 内存
Claude：   200K tokens ≈ 15 万字 ≈ 500 页 A4 纸

这 200K tokens 的"内存"里装着什么？

占用来源类比说明
CLAUDE.md 和 rules/开机自动启动的常驻程序每次对话都会加载，一直占着空间
对话记录你打开的应用越来越多聊得越久，占用越多
读取的文件内容打开的文档让 Claude 读一个 1000 行的文件 = 吃掉一块内存
命令执行输出日志输出跑测试、装依赖的输出都会占空间

"内存"满了会怎样？

跟电脑一样 — 内存快满了，系统开始卡顿：

text 
电脑内存满 → 频繁 swap → 变卡 → 应用响应慢
Claude 上下文满 → 自动压缩 → 可能丢细节 → 回答质量下降

Claude Code 会自动压缩（auto-compact）— 相当于系统自动关掉一些后台应用腾空间。你不需要手动干预，但它可能关掉你觉得"还要用"的东西。

动手：手动"释放内存"

与其让系统自动决定关什么，不如你主动管理。输入：

text 
> /compact

Claude 会把之前的对话总结成简短的摘要，释放大量空间 — 相当于你主动关掉不用的应用。

你还可以指定"哪些应用不要关"：

text 
> /compact 重点保留菜单 API 的设计决策和数据库 schema 的讨论

这样压缩后，关于菜单 API 的讨论细节会被优先保留，其他不太重要的内容被压缩掉。

什么时候需要手动 /compact？

text 
你在做一个跨多个文件的大改动 → "内存"快满了 → Claude 的回答开始变差
→ /compact 清理一下 → 继续工作

实际使用中，大多数简单任务（改个 bug、加个功能）不需要手动压缩。只有长会话（持续 30 分钟以上的复杂任务）才可能需要。

技巧：如果你发现 Claude 开始"忘记"之前讨论过的东西，或者回答质量明显下降，先试试 /compact — 就像电脑卡了先清一下内存。

现在先记住 /context 和 /compact 这两个命令。后面 5.6 构建订单系统时，你会在实战中真正用到它们。

动手：并行运行多个 Claude

打开两个终端窗口，都进入 waimai-app 目录，分别启动 Claude Code：

text

claude
> 帮我优化菜单列表的前端页面，卡片加上阴影和圆角

# 终端 2 — 做后端（另一个终端窗口）
cd waimai-app
claude
> 帮我优化菜品 API 的性能，加上按分类查询的数据库索引

两个 Claude 各自独立工作，互不干扰。同一个项目目录可以同时跑多个 Claude 会话。

并行的注意事项

可以：多个终端窗口各自启动新会话，独立工作。

不要：在多个终端恢复同一个会话 — 消息会交叉混乱。如果需要分支，用 -r 选择后各自发展。

并行适合任务独立的场景：一个窗口做前端、一个做后端、一个写测试。不适合多个窗口改同一个文件。

思考深度

动手：调整思考深度

在 /model 里选择 Opus 后，注意看 — 你可以用左右方向键调整思考深度（effort level）：

text 
← 低 (low)     中 (medium)     高 (high) →
深度效果适合场景

动手：对比不同思考深度的效果

先切到 Opus（/model → 选 Opus），思考深度设为 low（左方向键），输入：

text 
> 我们的订单创建 API 有个潜在问题：如果两个用户同时下单购买同一道菜品（库存只剩 1 份），
  会不会出现超卖？帮我分析一下并给出解决方案

观察 Claude 的回答 — low 模式下它可能只给出表面的解决方案（比如"加个 if 判断"）。

现在把思考深度调到 high（/model → 右方向键），输入同样的问题。

对比差异：

  • low：回答快，但可能忽略并发细节（数据库锁、事务隔离级别）
  • high：回答慢，但会深入分析竞态条件、给出数据库事务 + 乐观锁/悲观锁的完整方案

注意：这个对比需要用 Opus，因为思考深度调节目前仅 Opus 支持。

什么时候调低？什么时候调高？

思考深度适合的任务外卖项目示例
low改变量名、加注释、格式调整"帮我把 price 字段改名为 unitPrice"
medium常规 CRUD、普通功能开发"帮我写个按分类查询菜单的 API"
high复杂逻辑、并发问题、架构设计"订单金额算不对，帮我排查所有可能的原因"

大多数时候不需要手动调 — Opus 默认就是 high。只有在觉得等太久、任务又不复杂的时候，才考虑调低。

思考深度影响的是推理质量，不是回答长度。low 不代表回答短，high 也不代表回答长。它影响的是 Claude 在回答前"想多久"。

动手：用 Plan 模式规划复杂任务

按 Shift+Tab 切到 Plan 模式（底部显示 ⏸ plan mode on），然后输入一个复杂任务：

text 
> 我想给外卖系统构建完整的下单流程：
  - 从购物车页面点击"去结算"，进入订单确认页
  - 订单确认页显示已选菜品、数量、总价
  - 点击"提交订单"创建订单，跳转到订单详情页
  - 订单详情页显示订单状态、菜品明细、总价

Claude 在 Plan 模式下不会直接动手改代码。它会：

  1. 分析当前项目结构和已有代码
  2. 列出需要修改和新增的文件
  3. 给出分步实施方案（先做什么、后做什么）
  4. 标注可能的风险点（比如需要改数据库 schema、影响已有接口等）

你审查方案后，觉得 OK，再切回 Normal 或 Accept Edits 模式让它执行。这个下单流程会在串联练习中实际构建出来。

为什么复杂任务要先 Plan？

text 
不 Plan：
你：构建完整的下单流程
Claude：（直接开始改代码... 改了 10 个文件... 方向不对... 回滚重来）

先 Plan：
你：构建完整的下单流程
Claude：（分析后给出方案）我建议分 4 步：先建表 → 再写 API → 然后前端页面 → 最后测试
你：第 3 步的页面设计我想调整一下...
Claude：好的，调整后的方案是...
你：OK，开始执行

先 Plan 的好处：在动手之前发现方向错误，比改了 10 个文件后再回滚便宜得多。

Plan 模式的适用场景

场景用 Plan？
改个 bug、加个字段不用，直接做
新增一个完整功能模块用，先出方案
重构涉及多个文件用，先列出影响范围
不确定怎么实现用，让 Claude 出几个方案对比
